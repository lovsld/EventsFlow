# EventsFlow V0.2-A 架构说明

按代码的实际落地结构写（`v02/` 包），并对照任务书 §十二的建议结构。
任务书的建议结构是针对一个假想布局写的（`src/` + `agent_brain.py`
等），其自身规则是「以实际代码为准」，故本文以实际模块为准、逐项
给出对应关系。Phase 1 的逐项审查见 `V0.2-A_PHASE1_REVIEW.md`。

## 1. 总览

```
characters_v02/<id>/     角色数据（profile/personality/principles/goals）
characters_variant/      变体场景角色数据（实验 3b，纯数据）
scenarios/               变体场景世界配置（JSON 数据）
        │
        ▼
v02/config.py ── load_all() 扫描角色目录 → CharacterConfig（含 all_ids）
        │
        ▼
v02/runner.py ── run_simulation(mode, ticks, seed, characters_root?,
                 world_config?, suppression_rules?, resume/loop…)
        │  组装 WorldEngine / CharacterAgent×N / EventBroker / Store
        ▼
v02/scheduler.py ── asyncio 事件驱动：每 tick 一次 world.step() 提交
        │
        ├─ v02/world.py        WorldEngine + Action Resolver（唯一提交者）
        ├─ v02/world_config.py 世界静态结构单一数据源（地点/邻接/景物/物品/环境事件）
        ├─ v02/broker.py       Event Broker：感知规则 + (agent,event) 去重 + 反事实抑制
        ├─ v02/interaction.py  Interaction Manager：会话/发言权/打断
        └─ v02/agent.py        CharacterAgent：感知→解释→预测评估→决策→计划
```

## 2. 模块对照（任务书概念 → 实际模块）

| 任务书概念 | 实际落点 | 说明 |
|---|---|---|
| World Engine | `v02/world.py::WorldEngine` | 唯一能提交客观状态者；`step()` 只由 Scheduler 调用 |
| Action Resolver | `v02/world.py::resolve()` | 主动性排序、目标离场发言失败、搜查/展示已数据驱动（按物品客观位置/持有者判定） |
| 世界配置 | `v02/world_config.py` | V0.2-A 新增：地点、邻接（原四份副本已收敛为一）、景物、关键物品初始态、环境事件 |
| Event Broker | `v02/broker.py` | 同房间完整事件 / 相邻仅模糊声 / 其余无；投递去重与抑制均留审计记录 |
| Perception | `v02/broker.py::build_perception` | 与 Broker 同模块（V0.1 规则逐字移植） |
| Agent Runtime | `v02/agent.py::CharacterAgent` | 独立认知：私有状态、解释、预测评估、计划/目标联动 |
| Context Builder | `v02/context_builder.py` | provider 唯一可见输入；含 available_actions 计算与 M4c 匹配函数 |
| Decision 协议 | `v02/protocol.py` | AgentDecision/ActionSpec/PlanUpdate 严格校验（extra=forbid）；含 selected_goal_id |
| LLM Provider 层 | `v02/providers/` | base（接口+错误类型）、rule、mock、gemini、openai_provider（deepseek/kimi/qwen/openai 四预设共用 OpenAICompatibleProvider） |
| Memory Manager | `v02/memory.py`（Agent 记忆与信念）+ `v02/memory_manager.py`（重要性/长期晋升） | 信念证据化在 memory.py（见 §3） |
| Belief Manager | `v02/belief_manager.py` | 预测错误 → 信念/信任 的确定性规则表 |
| Prediction Engine | `v02/prediction.py` | 结构化预测（5 个可核查字段）+ 加权 PredictionError |
| Plan Manager | `v02/plan_manager.py` | 计划状态机（active/blocked/completed/abandoned）、承诺衰减、结果驱动步进、Goal 生命周期联动、替换门控记账 |
| Goal 系统 | `v02/protocol.py::Goal` + `v02/plan_manager.py` 生命周期 | 结构化运行时对象，确定性生命周期（见 §4） |
| Persistence | `v02/persistence.py` | SQLite（可切 PostgreSQL）：decisions/events/predictions/belief_changes/plan_transitions/goal_changes/consolidations/suppressions… |
| Checkpoint/Resume | `v02/checkpoint.py` + runner | 每 tick 检查点；--resume 按 checkpoint 回滚 DB 后重放 |
| Experiments | `v02/experiments.py` + 根 `experiments.py`/`audit.py` | 种子组、反事实、指标聚合、STEP1 一致性审计 |
| Scheduler | `v02/scheduler.py` | asyncio 事件驱动、SubmissionGate、--loop 额度等待 |

与任务书建议结构的差异（均为审查第 9 节确认的不采纳项）：不做
`src/` 重组（包名保持 `v02/`）；配置前缀保持 `ACP_*`（不改名
`EVENTSFLOW_*`）；不建 LLM 路径的效用打分模块（LLM 只提意图，
效用评分是 rule provider 的内部实现）；不预建 give/take 语义
（动词表占位保留，Resolver 按普通事件处理）。

## 3. 信念：证据模型

`Belief{key, confidence, kind, desc, evidence[]}`，evidence 条目：
`{source_event_id, source_type, reliability, observed_at, source}`。
source_type 五类与 kind 的映射（direct_observation/direct_interaction
→ experienced；testimony → heard；inference/assumption → inferred）
及重算规则（同事件去重、按独立通道分组、组内取最大、组间 noisy-OR、
钳制 (0,1]）见 `v02/memory.py` 与 `V02A_PHASE3_REPORT.md` §2。
任何置信度变化都落 `belief_changes` 表：预测错误路径
（cause=prediction_error）与解释路径（cause=interpretation）都覆盖，
`Store.chain_for()` 可从 DB 单独复原任一决策的完整因果链。

## 4. Goal 与 Plan

Goal 是运行时对象（status/progress/commitment/created_at/deadline），
但生命周期只由确定性规则驱动：与 goal key 对齐的计划事件
（set/步进/完成/abandon）推动它，变更落 `goal_changes` 表。LLM 与
rule 都不能自由增删目标；决策层的 `selected_goal_id` 只能指向既有
目标且经运行时归属校验。Plan 在 active 之外新增 blocked（步骤连续
失败达阈值），高承诺计划（commitment ≥ 0.7）受替换门控保护——
普通信息事件只能留下被拦截的记录，关键新信息才可替换。

## 5. 校验分层（V0.2-A 加固后）

1. 协议层：未知字段拒绝（extra=forbid）、枚举严格；
2. provider 层：JSON 修复重试（计数入 repair_count），回退为
   降级 wait 并记录 error；
3. 运行时层（decide）：selected_goal_id 归属校验（全 provider）、
   LLM 行动 available_actions 成员校验（仅真实 LLM）；
4. 世界层：Resolver 对动词/地点/邻接/同场/持有做最终裁定。
任何一层拒绝都产生审计记录，不存在静默放行。

## 6. 情绪与人格的实际口径

运行时情绪 = `emotions{arousal, suspicion}` 两标量 + 关系中的
per-agent trust（0–1）。写点：预测错误规则表（belief_manager）、
感知到的拒绝/质问（agent 解释路径）；读点：rule provider 效用与
speech_prediction 的拒绝预期、上下文呈现。**没有**六维心理学模型，
也不打算扩建。人格五维中 caution/curiosity/impulsiveness/
sociability 均有实际读写点；**honesty 至今没有任何读取点，是未
生效维度**——配置里保留只是数据完整性，不要据此推断行为。

## 7. 场景即数据

角色（characters 目录）、世界（world_config dict）都是数据：
`run_simulation(characters_root=…, world_config=…)` 可整组替换。
决策代码中仍与酒馆剧本绑定的部分（已知限制，实验 3b 实证）：
`agent.py::_interpret` 的断言解释表、`agent.py` 发现信件的计划
分支、`context_builder` 的 show 可用性（owner+信件）、rule
provider 按角色 id 分支的话语/搜查候选。这些属于「剧本内容层」，
不在通用决策内核内；其边界见实验报告。
