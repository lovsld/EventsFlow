# V0.2-B 架构落地说明

本文记录 V0.2-B（B1–B3 实施 + B4 场景 A/B 评测与冻结）实际落地的
架构与数据契约。设计意图以 `docs/V0.2-B_DESIGN.md` 为准；本文只写
**代码里真实存在的东西**，并逐条标注与设计文档的差异（§7）。
场景 C 由独立执行方仅凭本文与 schema 完成——本文即其契约依据之一。

## 1. 总原则（已落地）

- **四层分离**：Action 成功（Resolver 的 ok）≠ Plan Step 完成
  （StepEvaluator 对 success_condition 的判定）≠ Plan 完成（全部步
  fulfilled/skipped）≠ Goal 完成（GoalEvaluator 对 success_condition
  的判定）。四层各有独立判定点，互不代写。审查的 P0 以具名回归
  测试钉死（`test_v02b_b3.py::test_p0_search_ok_found_nothing_is_not_step_fulfilment`、
  `test_v02b_b2.py::test_searched_but_not_found_does_not_complete_the_goal`）。
- **场景语义只存在于数据**：claims、objects 能力位、目标条件、计划步
  条件全部是场景/角色数据；通用代码（conditions / scenario /
  goal_engine / plan_evaluator / rule_provider）不含任何角色 id、
  claim 字面量或地点字面量分支。
- **解释层不设立计划**：言语感知走三条通用通道（命题证据 / 言语行为
  效应 / 矛盾推断），计划只能由 provider 的 plan_update 或规则路径的
  计划合成器产生。

## 3. 数据契约

### 3.1 Scenario Definition（`scenarios/*.json` 或 world_config 内嵌）

字段：`scenario_id, version, comment?, locations, adjacency,
scenery{loc: [id | {id, searchable}]}, objects{id: {location, holder,
seen_by, searchable, movable, displayable, on_found: inspect|acquire,
fact_belief, reveals[{belief, reliability}]}}, claims{id: {proposition,
stance: assert|deny|inquire, base_reliability, sensitive,
speaker_belief?, basis_required?=true, speaker_min_confidence?,
speaker_kind?}}, speech_lines{claim_id: [lines]}, ambient[]`。
加载时 Pydantic 校验 + 目标条件的主观域校验（决策路径条件出现
objective 标记即拒绝加载，报错指名角色与目标）。

### 3.2 谓词词表（封闭集，`conditions.py`）

叶子：`object_possession{object, holder: self|<agent>|any}`、
`object_at_location{object, location}`、`object_found{object}`、
`belief_threshold{belief, min_confidence, min_source_tier?}`、
`agent_at_location{agent: self|<agent>, location}`、
`event_occurred{event_type(别名 type_), actor?: self|<agent>|any_other,
target?, claim?, topic?, object?, location?, within_ticks?, count?}`、
`trust_threshold{other: <agent>|any, min_trust}`、
`goal_status{goal, status}`；组合子 `all/any/not`。
满足度 ∈ [0,1]：belief/trust 叶连续（conf/θ 钳制），其余 0/1；
min_source_tier 未达 → ×0.5 且不算 satisfied。`satisfied` ⇔
evaluate ≥ 1.0；`progress_of` 递归（all=子项均值，any=子项最大值）。

主观语义要点：`object_possession(holder=他人)` 读信念
`holds:<holder>:<object>` ≥ 0.9 且须 direct 级证据；
`object_at_location` 只认亲眼所见记录（object_sightings），
注册表位置不是知识；`event_occurred` 只读 perceived_events /
own_actions 两本主观账。

### 3.3 Goal（protocol.Goal 扩展，全部新字段带默认值）

`kind: achievement|maintenance`、`status: inactive|active|paused|
completed|failed|abandoned`、`activation_condition / success_condition
/ failure_condition`（谓词 dict 或 null）、`priority_current`
（运行时优先级，init=weight；weight 永不变）、
`priority_rules[{when, delta, once}]`（无状态重算，once 闩锁）、
`progress`（achievement 的条件满足度；maintenance 不写）。
GoalEvaluator 顺序：inactive→active；failed 先于 completed；
achievement→completed；暂停规则（被另一目标的关联计划顶替→paused；
重新获得关联计划或成为优先级第一且无当前计划→reactivated）；
priority_current = clamp(weight + Σ当前生效 delta, [0, 1.5])。
变更落 `goal_changes` 表（kind: activated / goal_progress /
goal_completed / goal_failed / goal_paused / goal_reactivated /
priority_change / goal_abandoned）。

### 3.4 Plan / PlanStep（protocol）

PlanStep：`step_id, objective, action_candidates[模板 dict],
success_condition, failure_condition(可带 "terminal": true),
retry_policy{max_attempts=2, on_exhausted=replan, reactivate_when?},
status: pending|active|fulfilled|failed|skipped, attempts`。
字符串步自动包装为 legacy 步（step_id=`legacy:<i>`，
success_condition=None）——**legacy 步从不被 StepEvaluator 判定、
从不 blocked，只能由 provider advance 推进**。
PlanState：`goal_id`（稳定关联；来源仅三：合成器、set_plan 参数、
经所有权校验的 PlanUpdate.goal_id，缺省继承被替换计划的链接）、
`blocked_info{reason, since_tick, step_id}`、`pending_recovery
{strategy, source}`、`reactivate_when`、`retry_recoveries{step_id: n}`、
status 含 `suspended`。

失败计数（§5.4 精确语义）：一次评估计一次失败 ⇔ 行动与当前步模板
一致 ∧ 成功条件未满足 ∧（失败条件满足 ∨ 结果 ok=False ∨（无失败
条件 ∧ 成功条件至少一叶决定性为 0））。环境重置：新感知事件命中
当前步条件引用集（对象/地点/角色/命题）→ attempts 清零并落
`environment_reset`。blocked 进入：attempts ≥ max_attempts ∨
terminal 失败条件；同时按 retry_policy.on_exhausted 调度默认恢复。

恢复合法转换（PlanManager.execute_recovery，全部落 kind=recovery）：
retry（attempts 清零；同一计划同一步最多 2 次，超限拒绝）、
replan（须同决策给出替代步，否则 recovery_deferred；旧计划以
reason="replanned" 关闭，新计划继承 goal_id）、suspend（须
reactivate_when；policy_default 时默认取当前步 success_condition；
GoalEvaluator 每轮求值时检查，满足→reactivate）、abandon（须理由；
只关计划，不动目标）、skip（当前步标 skipped；完成记录携带
skipped 计数）。provider 的显式 recovery（PlanUpdate.recovery）
在 decide() 中先于默认策略执行。
**advance 语义变更（破坏性，已在代码与 LLM 契约中标注）**：
对 blocked 计划 advance → `advance_rejected_blocked`；对条件步
advance → `advance_rejected_conditional_step`；仅 legacy 步可被
provider advance 推进（签名去重保留）。

### 3.5 决策记录新增落盘

`agent_decisions.candidate_scores`（可空 JSON 列）：规则生成器
top-5 候选 {action_sig, total, factors, jitter, source, goal_key}
+ 最终选择。旧 run 读为 None。

## 4. 规则路径候选与效用（摘要）

候选四源：目标叶模板（按未满足叶生成 search/move/ask/speak/
confront/show 的通用模板；维护目标只产生风险修正项）、当前计划步
模板、社交回应（待答问题走披露门槛三选一：assert/deny/deflect）、
基线（observe/listen/work/wait，work 话题来自 profile.routine）。
效用 = 0.9·GoalAlignment + 0.55·InformationValue + 0.45·Personality
+ 0.40·Emotion + 0.35·PlanConsistency − 0.8·Risk − 0.8·Social
− RepetitionPenalty（言语/搜查 0.22/次，其余 0.05/次），
jitter ≤ 0.18（种子键控）。计划合成：当最高优先级**成就**目标
（带 success_condition）无计划服务时，按叶的固定谓词序合成
[locate 步, act 步 / gather 步 / move 步]，goal_id=该目标 key。

  scenario 转储；`--resume` 在 mode/backend 之后校验 engine_version，
  不符（含缺失）拒绝续跑。
- V0.1（`src/`、`tests/`）零改动；`runs_v02/rule_v02a_seed42` 等
  既有轨迹只读保留；新规范轨迹 `runs_v02/rule_v02b_seed42`。

## 6. LLM 契约

SYSTEM_TEMPLATE 与 _JSON_CONTRACT 收敛为单一共享常量
（openai_provider 定义，gemini_provider 导入），一致性测试断言
两后端呈现同一契约文本。契约显式声明 B3 语义：goal_id 链接、
recovery 五策略、advance 对 blocked/条件步无效。

## 7. 与设计文档的差异（逐条，待追认）

1. **claims 模式补全**：设计未定义「谁有资格断言什么」，落地时为
   ClaimDef 增加可选字段 `speaker_belief`（默认=proposition）、
   `basis_required`（默认 true；false=无据可断言，诚实度计入
   SocialCost）、`speaker_min_confidence`、`speaker_kind`。无此
   补全，涌现链第一环（老板的 mayor_hint）与反事实目标话语在
   通用生成器下不可产生。
2. **三个信念无通用写者**：`letter_known_by_others`、
   `being_investigated`、`mayor_deal_risky` 在三条通道下无写者，
   §4.6 中引用它们的条件在**数据层**用既有谓词等价改写
   （event_occurred 组合），未新增谓词、未加解释规则。
3. **scenario 注入 rule provider 走属性而非 DecisionContext**：
   上下文即 LLM 提示词，Phase-4 隔离测试禁止无知角色的提示词出现
   目标命题；provider.scenario 由 runner 设置，上下文只带无泄漏的
   {locations, adjacency}。
4. **§4.6 目标条件与 PlanStep 协议提前至 B1 落地**（B1 的生成器与
   合成器即条件驱动，属阶段内必要前置）；GoalEvaluator 本体仍在 B2。
5. **holdings 初始值收窄**：设计 §3.2 的初始 holdings 含「场景注册
   holder==自己」，落地删除该项——仓库钥匙注册在 keeper 名下却
   客观丢失，计入持有会使占有目标在搜查前即满足。初始 holdings
   仅 profile.possessions ∩ 场景对象，之后由获取/感知维护。
6. **Registry 的 search 提供规则为风景级**：search 仅当当前地点有
   searchable 风景条目时提供（无泄漏口径）；对象级 searchable
   由 Resolver 在执行时把关。
7. **Resolver 能力位缺省**：场景未声明的对象保持 legacy 行为
   （searchable/displayable=True）；声明对象严格按位。
8. **gain_business 成功条件降级**：按 §4.6 自带逃生口，仅
   belief_threshold(business_opportunity ≥ 0.5)。
9. **maintenance 的 progress**：Goal 模型默认 0.0（V0.2-A 测试钉
   住），求值器从不为维护目标写 progress，指标按 kind 区分——
   与设计「progress 为 null」是表示法差异，无语义差别。
10. **refuse 的信任代价**作用于 target ∈ (None, self)：无 target
    的旧夹具事件按「对感知者说」计；真实运行 Resolver 恒设 target。
11. **ScenarioDefinition 允许 `comment` 字段**（自由注记，代码
    忽略），使带注释的真实场景文件能通过 extra=forbid 校验。
12. **计划合成目标的选择**：generate_decision 对「最高优先级成就
    目标（带 success_condition）」合成——维护目标居首时不令合成
    饿死（B3 门槛调试中发现的通用机制缺口，非场景语义）。
13. **suspend 的 policy_default 条件来源**：取当前步的
    success_condition（provider 显式 suspend 仍必须自带
    reactivate_when，否则拒绝）。
