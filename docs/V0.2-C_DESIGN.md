## 1. 主张核验

任务书 §一列出 6 个问题。逐条判定如下（总表先行，证据在后）。

| # | 主张 | 判定 |
|---|---|---|
| 1 | 多个目标相互暂停、目标饥饿 | **成立** |
| 2 | 知情 Agent 不能可靠回答问题或主动传递信息 | **成立** |
| 3 | Agent 缺乏目标驱动的自主探索行为 | **部分成立** |
| 4 | Plan 粒度偏粗，Replan 成为主要动力学 | **成立** |

### 1.1 主张 1：目标互暂停与饥饿 —— 成立

**触发机制（代码级）**。暂停不由任何「调度器」决定，而是
GoalEvaluator 的一条反应式规则（v02/goal_engine.py，paused rule）：
任一 achievement 目标处于 active、且 agent 当前计划的 goal_id
是另一个目标时，该目标在下一次 evaluate 时被置 paused。求值点
共四处（v02/runner.py init、agent.receive() 两次、agent.decide()
在 plan update 之后 cause="plan_event"）。

**诊所 tick 0 全路径（专项核查 A，逐步可复现）**：

1. init 求值：医生两个 achievement 目标均无激活条件，同为
   active（ensure_readiness 权重 1.0、brief_nurse 0.85）。
2. tick 0 decide()：context 只呈现 active 目标；rule provider
   的计划合成（_maybe_synthesize）只为最高优先级目标
   （ensure_readiness）合成计划，PlanUpdate(replace,
   goal_id=ensure_readiness) 落盘，current_plan 建立。
3. decide() 随即以 cause="plan_event" 再求值：brief_nurse
   active + plan.goal_id ≠ brief_nurse → **paused**，reason
   与诊所 run 的 goal_changes 记录逐字一致：
   `plan pursuit switched to ensure_readiness (cause=plan_event)`。
4. 此后 brief_nurse 永不恢复，三个结构性原因叠加：
   - 恢复条件（同文件 reactivation 分支）要求 current_plan 为
     None、或计划归它所有；ensure_readiness 的计划在诊所里
     从未消失（blocked→replan 循环持续供给，见主张 4）；
   - context_builder 只把 status="active" 的目标放进
     DecisionContext.active_goals，paused 目标连 constraints
     备注都不出现（_inactive_goal_notes 只覆盖
     inactive/completed/failed/abandoned）——**paused 目标对
     provider 完全不可见**，不产生任何候选、不被合成计划；
   - provider 的目标选择只在 active 集合内按 priority_current
     排序，paused 目标不参与。

**轨迹证据**：诊所 seed42 的 goal_changes 表中，医生 24 tick
**恰好只有 1 行**——tick 0 的 goal_paused。此后无 reactivated、
无 progress、无 completed。两颗种子一致（V0.2-B_SCENARIO_C §2）。

**精确化**：这不是「调度不公」，而是系统根本没有调度层：暂停
是计划易主的无条件副作用，无期限、无豁免、无数据侧字段、
恢复条件与计划生命周期强耦合。任务书 C1 的判断成立，且问题
比「公平性」更底层——**单计划槽 + 反应式暂停 + paused 不可见**
三者共同构成饥饿。

附带发现：Goal 模型的 `commitment` 字段（protocol.py，默认
0.8）**全代码无任何读取者**（grep 确认），是死字段；`deadline`
同样无到期语义（V0.2-B 已知限制沿袭）。C1 设计须显式处理这
两个字段的去留（见 §2.7）。

### 1.2 主张 2：知情者不能可靠回答 / 主动传递 —— 成立

分两个子机制核查，结论不同，须分开陈述。

**(a) 回答（Answer）：候选存在，但定价必输。**
_social_candidates（rule_provider.py）确实为「被点名提问且我
持有该命题的断言资格」生成回答候选，并带 obligation 加成
0.55（B 轮为修复「问而不答」加入）。但用诊所 run 自己的
candidate_scores 落盘可算清这笔账（seed42，医生被护工当面问
patient_inquire 的 4 个 tick：7/8/9/20）：

| 因子 | 回答候选（speak patient_notice）实测 |
|---|---|
| base（social 源） | 0.30 |
| obligation | +0.55 |
| goal | 0.0（social 候选无 goal_key） |
| info | **0.0** |
| personality（sociability 0.5） | +0.45×0.5 |
| social（披露成本） | **0.32**（=(0.5−0.3)×1.6） |
| **total（含 jitter）** | **0.97–1.00** |
| 实际被选中 | **observe**（4 次全败） |

两个结构性错误：
- **info 因子按「我自己的不确定性」计价**（_score 中
  info_f = 1 − 我对该命题的置信度）：我越是确知答案，回答
  的信息价值越被记为 0。回答的价值在**提问者**一侧，当前
  公式恰好把它算反。
- **披露成本不分场合**：第一手知识的披露成本
  max(0, disclosure_threshold − trust)×1.6 对「主动泄露」
  与「被当面问答」一视同仁；医生 disclosure_threshold=0.5、
  对护工 trust=0.3 → 0.32 的 social 因子（×W_SOCIAL 0.8
  ≈ −0.26 总分）。而他自己的 ask 候选（目标叶驱动）总分
  ≈2.3。obligation 的 0.55 在这个量级下只是把回答抬到与
  observe 掷币的水平。

另有一个候选**丢失**通道：pending_question 是**单槽**
（agent.state.pending_question），任一新 ask/confront 感知即
覆盖，且在每次 decide() 末尾无条件清空（agent.py「consume
pending question … answered or dropped」）——同一感知批次内
的第二个问题、或在 decide 选用其他行动时，问题即永久丢失，
连「拒绝」都不会发生。

**(b) 主动断言（Assert）：没有信息价值驱动的生成器。**
现行 assert 候选只有两个来源：
- 说话者**自己的**目标叶模板：belief_threshold 叶（我需要相
  信 P 时，模板里顺带生成向在场者 assert P 的候选——语义上
  是「说出我所信」，不是「告诉你所缺」）与 event_occurred
  {claim} 叶（brief_nurse 型目标——这条通道存在且是诊所的
  设计通道，但被主张 1 的暂停在 tick 0 掐断，且 paused 后
  连候选都不生成）；
- 上述回答路径。

**不存在**任何计算「我持有 X、对方可能不知道、X 对对方有价
值」的生成路径：生成器从不读对方的提问史/行为史来估计对方
的知识缺口（utterances_heard、perceived_events 里有这些主观
材料，但只被解释通道消费，不被生成器消费）。诊所里
patient_notice 进入 top-5 的 4 次全部来自回答路径（factors
带 obligation 可辨），目标驱动路径 0 次。任务书「claims 只
定义资格、不定义选择」的判断成立（V0.2-B_SCENARIO_C 缺口 1
原文），且可补一句：**连资格→候选的管线也只在两个窄口存在**。

**(c) 顺带核查：证词可靠度公式**。公式存在于代码
（agent._interpret_speech 通道 1：reliability = base ×
(0.4 + 0.6×trust)），但未进入面向场景作者的契约文档——诊所
作者只能盲猜阈值（缺口 3）。这是文档债，不是机制债；C2
阶段顺手清偿（§3.7）。

### 1.3 主张 3：缺乏目标驱动探索 —— 部分成立

**存在的部分**：目标驱动 search 是真机制且被证明过——
_leaf_candidates 对 object_possession/object_found/
object_at_location 叶生成 _search_route（有 sighting 去
sighting 地、无则枚举全部可搜地点、远处先 move），仓库 B1
门槛正是靠它通过（keeper tick 1–3 移动→搜查→得钥匙，分数
逐条归因于目标叶）。belief_threshold 叶在命题挂接 fact
object 时也生成 search_route。「完全没有目标驱动探索」不
成立。

**缺失的部分**（诊所 search=0 的真实成因是三层叠加）：
1. **上游断供**：search 候选只从「active 目标的叶」与「当前
   计划步」生成。护士的 restock_medicine 从未激活（主张 2 的
   下游），她其余目标（finish_chart 的 location+work 叶、
   maintenance）不产生任何 search 模板——她站在 pharmacy 里
   也没有 search 候选。144 次决策 top-5 中 search 出现 0 次
   （SCENARIO_C §2），与此结构完全一致。
2. **覆盖面窄**：object_possession 且 holder=他人 时只有
   observe/ask 模板（不搜）；belief 叶无 fact object 时不搜；
   「为确认/排除一个信念而搜」只在 direct-tier + fact object
   的窄条件下成立。
3. **无无指向探索**：没有任何「空闲时搜一个没搜过的地方」
   的基线探索候选——admission_form 这类「第二通道」物品
   （无人目标指向、靠发现）永远无人碰：诊所里它静静躺在
   oncall 24 tick。searched_empty_places 状态与「已搜」折扣
   （info 0.15）已存在，但只用于给已生成的 search 候选打折，
   不产生探索行为本身。

判定：机制存在、覆盖面与触发面不足，且失效模式与上游强耦
合——**部分成立**。C3 的任务因此是「统一信息价值 + 扩触发
面」，不是「从零造探索」（§4）。

### 1.4 主张 4：Plan 粒度偏粗、Replan 主导 —— 成立，且根因比任务书所述更深

**粒度（代码级）**：synthesize_steps（rule_provider.py）把
目标的 success_condition 叶**原样**当步条件：
- belief 叶 → `gather:<belief>` 步，success_condition = 该
  belief_threshold 叶本身（模板 ask/observe/listen/confront）；
- agent_at_location 叶 → `go:<loc>` 步，条件 = 该叶本身；
- event_occurred/trust 等其余叶 → `advance:<i>` 步，条件 =
  该叶本身；
- 只有 object 叶做了真分解：`locate:<obj>`（条件
  object_found）+ `secure:<obj>`（条件 = 该叶本身）。
即除 object 叶外，「步完成」与「目标叶满足」是同一件事——
酒馆规范轨迹步完成率 ≈0.028（V0.2-B 报告 §8.2）正是此结构
的度量。

**Replan 主导（轨迹级，诊所 seed42 plan_transitions 实测）**：
医生 24 tick 内 plan set ×6、blocked ×6、recovery ×5、
abandon ×5（replan 遗体）、step_evaluated ×18。他的
ensure_readiness 计划反复「建→卡→重建」；仓库 traveler
24 tick blocked 6 次（B 报告 §8.2）同型。

**两个比任务书更深的根因**（本阶段新定位，C4 的真正靶子）：
- **根因甲：「决定性为假」即失败**。plan_evaluator 的计数
  失败规则 (c)：无 failure_condition 且成功条件任一叶
  satisfaction 恰为 0 → 记一次失败。对 belief 叶而言，
  置信度 0（还没得到任何证据）就是 sat=0——**「尚未取得」
  被记作「尝试失败」**。医生的 gather 步：每次 ask 都是步
  一致行动、叶恒为 0 → 两次 ask 即 attempts=2=max_attempts
  → blocked → 策略缺省 replan。步甚至不需要「做错」任何事
  就会卡住。
- **根因乙：步评估是单发时间窗**。步的判定只发生在「做出
  该步行动后的下一次 receive」（agent._pending_step_check
  一次性消费）。ask→对方下 tick 才回答→回答到达时步判定
  早已消费完毕——**多 tick 插曲（问→等→答）在结构上无法
  完成任何步**；gather 步唯一能被满足的路径是自己的行动
  结果（search 找到东西），与它的模板（ask 为主）自相矛盾。
- 另：replan 无跨计划记忆——set_plan 每次都是全新
  PlanState（attempts、retry_recoveries 全部清零），
  synthesize_steps 对同一目标+同一视图是确定性函数 →
  **同一计划可被无限重建**，B3 的 retry 上限被 replan 整体
  绕过（任务书 §6.4 验收 4 所指）。环境变化重置
  （environment_reset，诊所实测 ×4）是唯一的天然刹车，不
  足以成环控制。

### 1.5 主张 5：Goal Progress 瞬时量、会倒退 —— 成立

conditions.progress_of 是当前视图的纯函数，**无任何闩锁**：
agent_at_location 叶读 view.location（瞬时）、
object_at_location 读 sightings、belief_threshold 读当前置
信度——全部可逆。goal_engine 对 achievement 目标每轮重算
progress，|Δ|≥0.001 即落一行 goal_progress，**下降照记**。
诊所实测（seed42 goal_changes）：护士 finish_chart 的
progress 在 tick 8→0.5、9→0.0、21→0.5、22→0.0 四次横跳
（其 success = all[agent_at_location(self,oncall),
event_occurred(work,self)]：work 叶是历史量恒 0/1，location
叶随她进出 oncall 闪烁，均值即 0↔0.5）。

精确化：event_occurred / object_found 叶本身是历史累积量
（perceived_events / found_objects 只增），天然闩锁；倒退只
来自**位置类与持有类与信念类叶**。修复因此不必推翻
progress 定义，但必须决定语义：见 §2.6 的单调化裁决（列入
开放决策 #2）。

### 1.6 主张 6：缺真实 LLM 完整证据 —— 成立

B 的 §十复验（V0.2-B_EXPERIMENT_REPORT §9）Plan 组「Rule
与 LLM 均能处理阻塞」记**部分**：LLM 侧只有契约文本与 mock
回归。唯一一次全程真实 LLM 运行（llm_full20_planlayer_
seed42，60/60 决策）跑在 **V0.2-A 时代的决策栈**上，先于
B 的 Goal Engine / 条件步 / 恢复状态机存在；B 栈（及将来的
C 栈）上的真实 LLM 轨迹为**零**。legacy 步占比、LLM 自由文
本计划与结构化步评估的相互作用，在现行栈上无任何实测。
任务书 §十一 #10 的要求（至少一组真实 LLM 端到端实验）确
为未偿债务；实验设计见 §8。

### 1.7 指标差距总览

§八清单 25 项与现状的差距（全表见 §7）：Goal 家族大半已
有（激活/追求/完成/失败/切换），缺**饥饿计数、暂停时长、
放弃率（现只有计数）**；Plan 家族大半已有（步完成/阻塞/
恢复/重试/replan 率），缺**重复指纹计数、死循环检出计数**；
**Communication 家族 7 项全部缺失，Exploration 家族 6 项
基本缺失**——且这两家的「候选生成率」类指标有一个共同的
落盘缺口：candidate_scores 只存 top-5 + chosen（rule_
provider.generate_decision 的落盘形状），**第 6 名开外的候
选生成事实不存在于任何产物中**，生成率不可算。这是 §7 中
唯一需要新增落盘底层的项（candidate census，§3.6）。

## 2. C1 设计：Goal Scheduler

### 2.1 兼容性裁决（任务书要求先于实现解决的问题）

现状的权力分布：GoalEvaluator 是目标**状态**的唯一写者；
provider 是目标**选择**的实际决定者（在 active 集合内按
priority_current 取首位并为之合成计划）；PlanManager 管计
划的对账与提交；暂停是 evaluator 对「计划易主」的无条件
反应。四者无一可单独改动而不牵动其余三者。裁决：

- **新增 GoalScheduler，但不新增状态写者**。Scheduler 是
  纯函数组件（新模块 v02/goal_scheduler.py）：输入 =
  (goals, current_plan, belief/plan 视图摘要, tick)，输出 =
  ScheduleDecision{pursuit_goal_id, eligible_goal_ids,
  utilities 表, 保护事件清单}。它**不写任何目标状态**；其
  结论经两条既有通道生效：① context extras
  （scheduled_pursuit_goal_id 等）→ provider 据此选目标与
  合成计划；② evaluator 在每个既有求值点先问 scheduler
  的暂停政策（may_pause），再执行状态转移。GoalEvaluator
  仍是唯一状态写者，plan_transitions/goal_changes 落盘形
  状不变。
- **暂停从「反应式副作用」降级为「政策决定」**。evaluator
  的 paused rule 改为：目标被计划易主挤出时，先查政策——
  scheduling.pausable=False 或已达 max_pause_ticks 或饥饿
  保护触发 → **不暂停**；此时争用转移到计划层解决：新追
  求目标要计划，现任计划按 PlanManager 既有 `suspended`
  语义挂起（reactivate_when 已在 B3 落地，酒馆/仓库轨迹
  证明可用）——即**争用优先在计划层用 suspend 消化，目
  标层 pause 退为最后手段**。这条裁决同时满足任务书
  验收 4（目标切换不丢失计划状态：suspended 计划的
  attempts/指纹原样保留，恢复时续跑）。
- **provider 的「首位目标」改为「调度追求目标」**。rule
  provider 现行 selected = priority 排序首位；改为：若
  context 带 scheduler 结论，selected := pursuit_goal
  （goal_f 对 pursuit 记 1.0，对次位 eligible 记 0.5，与
  现行 caliber 一致）。LLM provider 不受代码约束——
  context_builder 在 constraints 中增一行点名 pursuit
  目标与「paused 目标不得选」既有规则并列；LLM 不从则由
  既有 runtime 校验（selected_goal_id 所有权检查）兜底，
  偏离率由 §八指标如实记录。这是与 B 相同的不对称处理，
  不假装能强制 LLM。
- **求值点不变**：init / receive×2 的求值只做状态转移（激
  活/完成/失败/暂停政策）；scheduler 只在 decide() 内、
  PlanManager.reconcile 之后、build_context 之前运行一次
  （每决策至多一次，保证「每 tick 至多一次追求变更」的
  可审计性）。

### 2.2 depends_on 数据契约与语义

**与任务书示意的差异（重要）**：任务书示例写作「restock_
medicine depends_on brief_nurse」——但在诊所数据里这两者
分属**两个不同 agent**（护士与医生）。调度是单 agent 的
主观决策，一个 agent 无法调度他人的目标；跨 agent 依赖在
本架构中已经有正确的表达通道——激活条件读自己的信念
（restock 的 activation = belief fever_patient_coming≥0.4，
它等的正是医生传递的信息），且该通道在 B 中按设计工作、
只是从未被喂饱。因此裁决：

- `depends_on: list[str]` 只接受**同一角色自己的**目标
  key；加载期校验（scenario/config 加载时报错：未知 key、
  跨角色 key、**环路**——DFS 检环，环依赖直接拒绝加载，
  与「未知事实引用加载期失败」的既有数据纪律一致）。
- 语义两条，均为**调度语义，不改状态机**：
  1. **追求门控**：依赖未全部 completed 的目标不进入
     pursuit 资格集（它可以是 active、可以积累 progress，
     但 scheduler 不选它、provider 不为它合成计划）。门控
     只卡追求，不卡激活——避免把 B 的激活语义再改一遍。
  2. **依赖牵引（dependency bonus）**：未完成的前置目标
     获得其等待者（active 且未完成、且把我列入
     depends_on 者）的优先级牵引（公式见 §2.4）。这正是
     诊所需要的方向：医生 declare ensure_readiness
     depends_on [brief_nurse] 后，是 **brief 被 ensure
     牵引上来**，而非 ensure 被压住不管。
- 诊所数据改动（C1 阶段，仅数据、不动代码即可先行验证
  契约）：医生 ensure_readiness 增 `depends_on:
  ["brief_nurse"]`。这属于「数据契约的正当使用」，不是
  为诊所写特殊规则——同一机制对任何场景的任何同角色目
  标对成立。列入开放决策 #5 请 Hu 确认。

### 2.3 scheduling 块四字段：精确语义与缺省

落在 Goal 模型（protocol.py，全部可选、缺省即旧行为的安
全侧），随档案 YAML 声明：

| 字段 | 缺省 | 精确语义 |
|---|---|---|
| `pausable` | `true` | false 时 evaluator 的暂停政策恒拒绝该目标被暂停；争用转由计划层 suspend 消化（§2.1）。maintenance 目标本就不暂停（paused rule 只作用于 achievement），本字段对它们无意义、声明即忽略并在加载时警告。 |
| `priority_floor` | `0.0`（即无下限，旧行为） | evaluator 无状态优先级重算改为 priority_current = max(priority_floor, min(1.5, weight + Σdelta))。下限作用于**选择量级**，不作用于状态：它保证目标在 scheduler 效用中不沉底，但不豁免暂停（暂停豁免归 pausable/starvation 管）。 |
| `max_pause_ticks` | 全局缺省 8（config 可调） | 目标单次连续 paused 的 tick 上限。evaluator 在每次求值时检查 paused_since：超限即强制 goal_reactivated（reason="max_pause_exceeded"）并触发饥饿保护（§2.5）。None = 不设上限（配合 starvation_protection=false 的长尾目标）。 |
| `starvation_protection` | `true` | true 时：① max_pause 超限的强制恢复生效；② scheduler 对「从未被追求过的 active 目标」与「累计暂停超阈目标」给 aging 加成（§2.4 WAIT 项）。false = 该目标接受无限期等待（作者明示的背景目标）。 |

运行时附带状态（Goal 模型新增、缺省惰性、旧存档/检查点
按缺省补齐）：`paused_since: int|None`、
`cumulative_paused_ticks: int = 0`、`last_pursued_tick:
int|None`、`pause_count: int = 0`。四者都是 §八指标与
scheduler 的原料；checkpoint 序列化随 Goal dump 自动携带
（persistence 的 goal_changes before/after 已是全量 dump，
新字段自动入账，无需改表结构）。

### 2.4 效用公式的具体化

scheduler 对每个 pursuit 资格内的 achievement 目标算：

```
U(g) = priority_current(g)                                    [现有量: 权重+规则增量, 经 floor]
     + DEP × Σ_{h ∈ dependents(g), h active 未完成} priority_current(h)
     + WAIT × min(1, (tick − last_pursued_tick(g)) / WAIT_SCALE)   [从未追求记满格 1]
     + URG × 0                                                   [见下: 本阶段恒 0]
     − SWITCH                                            [g ≠ 现任 pursuit 且现任计划 commitment ≥ 0.7 时]
```

- **DEP（依赖牵引）缺省 0.6**：量级论证——诊所需
  brief(0.85 + 0.6×ensure 的 1.0 = 1.45) > ensure(1.0)，
  0.6 是满足该不等式并留出抖动余量的最小整洁值；最终值
  以 §2.8 校准实验为准。
- **WAIT 项**：last_pursued_tick 在 scheduler 选定 pursuit
  且 provider 确为其生成候选/计划时回写；WAIT 缺省 0.3、
  WAIT_SCALE 缺省 10 tick：10 tick 没轮到的目标最多 +0.3，
  足以翻转近似平局，不足以压过 0.85 量级的真实优先级差。
- **URG 置 0 的论证**：任务书示意的 Urgency 需要 deadline
  语义，而 deadline 在 B 中无任何语义且三场景数据无一使
  用；凭空发明「临近」度量是无据造机制。priority_rules 的
  增量已经是现行「情境紧迫」的表达通道并已进入
  priority_current。本阶段明确**不**引入 deadline 语义
  （见 §2.7），URG 项保留位置、恒 0，待真有带 deadline
  的场景数据再议。
- **SWITCH（防抖核心）**：见 §2.5。
- 确定性：同分按 goal key 字典序（与全栈 sorted() 纪律
  一致）；全部系数走 config（ACPConfig 或 scenario 级
  defaults），并随 run 落盘以便复盘（run_meta 增
  scheduler 系数快照）。

### 2.5 防抖与饥饿保护

三层，缺一不可（只靠 SWITCH 成本会被 WAIT 项逐 tick 顶
穿）：
1. **滞后门槛**：挑战者须 U > 现任 U + SWITCH_MARGIN
   （缺省 0.10）才易主；现任计划已完成/blocked 耗尽/现任
   目标失去资格时不受门槛限制（该让路时不许恋栈）。
2. **最短驻留 MIN_DWELL**（缺省 2 tick）：新选 pursuit 在
   2 tick 内不可被易主，除完成/失败/激活更高优先级新目
   标（activation 事件直接抢占——新激活目标本就带着情境
   相关性，这正是要它抢占的场合；抢占计入切换计数）。
3. **饥饿保护执行**：max_pause 超限的强制恢复目标在恢复
   后获得**一次保证追求窗**：scheduler 在接下来
   max(1, MIN_DWELL) 个 tick 内将其锁定为 pursuit（除非
   它完成/失败）；期间若它需要计划而槽被占，现任计划
   suspend。保证窗计入 goal_changes（reason 带
   starvation_protection 标记），§八的 Starvation Count
   以「恢复时 cumulative_paused_ticks 与最长单次暂停」双
   口径统计（§7）。

### 2.6 Goal Progress 单调化（主张 5 的修复，须 Hu 裁决）

方案：achievement 目标的 **progress 改为单调**——
evaluator 记录 progress = max(历史 progress, 本轮
progress_of(view))；goal_progress 落盘只升不降。完成判定
**不**随之放松：completed 仍要求当前视图 is_satisfied
（四层分离不受影响）。论证：progress 在本系统中的消费方
只有两个——人读的进度与 scheduler/指标的信号；倒退的进
度对两者都是噪声（诊所四次横跳即证）；而「世界真的倒退
了」（持有物被夺）由**叶级当前满足度**继续如实驱动候选
生成（未满足的叶照样生成模板），不依赖 progress 下降来
表达。反对案（保持瞬时 + 仅文档警告作者）不予采纳：任务
书 §十一 #6 明文要求「Goal 进度符合条件语义」，横跳进度
在指标层无法自洽（pursuit/completion 口径会被污染）。
此为一处**语义变更**，列开放决策 #2；若 Hu 否决，则降级
为「progress 保持瞬时、另增 progress_peak 字段供指标使
用」的备选，本文档 §7 的指标口径按主案书写、备选差异在
§7 注明。

## 3. C2 设计：Communication Candidate Generator

### 3.1 落点：新生成单元 + 旧评分市场，不设第二通道

生成：新模块 v02/comm_candidates.py，纯函数
`generate_comm_candidates(view, state 摘要, scenario,
config, tick) -> list[Candidate]`，由 rule_provider 在现
有 _social_candidates 位置调用（替换并吸收它），产出候选
与既有候选**同场竞价**（同一 _score 量纲、同一
searched/top-k 落盘）。不设独立通道的论证：B 的全部动力
学教训都指向「多市场必生套利缝隙」——若沟通候选自带选
择器，义务、性格、目标将在两个选择器间不一致。LLM
provider 侧不移植生成器（它自由生成），但 context 增
「待答问题 + 适用 duty」提示行，且 runtime 既有的
available_actions 校验不变；LLM 的义务履行率由 §八指标
如实度量（预期低于 rule，不掩盖）。

每个沟通候选打 `comm_kind` 标签（answer / assert / deny /
 clarify / ask / disclose / withhold），随 census 落盘
（§3.6）——这是 §八 Communication 家族的度量前提。

### 3.2 相关命题集（生成器的输入边界，信息隔离的守门处）

生成器只准从以下**主观**材料拼候选（全部取自说话者自己
的 view/state，逐项可审计）：
1. 待答队列中的问题命题（§3.3）；
2. 我自己的 active/paused 目标条件中出现的命题（叶引用）；
3. 我的 disclosure duties 命中的命题（§3.5）；
4. 我**感知到**他人询问过的命题（perceived_events /
   utterances_heard 中的 inquire 类）——「话题热度」来源；
5. 我亲历/持有高置信且与当前在场者**已现话题**相关的
   命题。

明确禁止：读他人 goals/beliefs/trust（运行时本来也无此
句柄——隔离不变量由既有测试守护，本设计不新增任何跨
agent 读路径）；用 objective world state 估计他人知识。

### 3.3 Answer 义务：从单槽到队列 + 义务的硬保证

- state.pending_question（单槽）→ **pending_questions
  队列**：元素 {asker, claim_key, proposition, tick_asked,
  addressed_to_me}；感知 ask/confront 时入队（只入点名我
  的；旁听问题入「话题热度」不入义务队列）；TTL 3 tick；
  被 answer/deny/refuse 任一回应后出队；过期出队并记一
  行审计（question_expired——「问题被系统遗忘」从此是可
  度量事件而非静默丢失）。checkpoint 迁移：旧存档的单槽
  在加载时包装成单元素队列（resume 字节同一性测试的处
  置见 §9.2——迁移只发生在旧检查点加载分支）。
- **义务的硬保证（生成层）**：队列中每个未过期问题，只
  要我持有其命题的任一合格 assert claim（资格判定 =
  ClaimDef 既有 eligibility：basis 置信 ≥
  speaker_min_confidence 等，不改），**必生成** answer 候
  选。生成是义务，选择不是——withhold/deny 候选同时生成
  （§3.5 的衔接），最终由评分裁决。验收「知道却无候选」
  的情形被构造性排除：eligibility 失败（我其实不知道/
  资格不够）不算义务违反，按 clarify 生成（§3.4）。
- **义务的定价修复**（对着 §1.2(a) 的两个结构错误）：
  1. info_f（answer/disclose 类）改按**受方估计**计价：
     对方点名问过 → 1.0；duty 触发 → 按 duty.urgency
     映射（high 1.0 / normal 0.7 / low 0.4）；主动类见
     §3.4。与旧公式的语义分野写进代码注释与架构文档：
     陈述类行动的价值在受方，提问类行动的价值在我方
     （ask 沿用 1 − 我的置信度，不变）。
  2. 披露成本分场合：social 因子中的披露成本系数，
     volunteer（主动）沿用 1.6，**answer（应答点名提问）
     降为 0.6**——社会规范上应答的披露门槛低于主动泄
     露，此为通用系数（对一切角色/命题同等适用），量
     值入 §2.8 同款校准（约束集追加：酒馆 owner 的保密
     链不得崩——seed 组中 denial/conceals 链路保持，
     见 §9.3 C2 阶段门）。
  3. obligation 加成保留 0.55 并改为**随等待时间增长**：
     obligation = 0.55 + 0.1 × 已等 tick（上限 +0.3）——
     问题越久没人理越难继续无视，给队列 TTL 一个评分侧
     的呼应。

### 3.4 Assert 的信息价值：只用主观状态估计「对方可能不知道」

这是本阶段公认的设计难点。方案：**感知史近似**。我对在
场者 T 关于命题 P 的 ignorance 估计，三档，全来自我自己
的感知史：
- 我感知过 T **询问** P（inquire）→ ignorance = 1.0
  （他公开承认不知道）；
- 我感知过 T **断言** P（assert，含转述）→ ignorance =
  0.0（他已知，不再生成对他的 assert 候选——重复告知
  从生成层掐断）；
- 无记录 → ignorance = 0.5（中性先验）。

Assert 候选价值 = ignorance(T,P) × relevance(P) ×
my_confidence(P)，其中 relevance(P) = P 在「我的目标叶 /
duty / 对话题热度」中的最大关联度（0–1，叶命中 1.0、
热度命中 0.5）。生成门槛：my_confidence ≥ 该 claim 的
speaker_min_confidence（资格既有规则）且 value ≥ 0.25
（通用阈值，入校准）。近似性的明示（必须写进架构文档，
不许假装精确）：此估计对「T 从别处刚学会 P 而我没在场」
必然误判（会多说一次），对「T 装不知道」必然误判——这
是**主观认知应有的误差**，与 B 的信念证据语义同源（角
色按自己的感知史行动，误差由世界纠正）。误差的后果有
界：多余 assert 只是多一次 testimony 事件，受方按证据
去重（同一命题同源证据不叠加）消化。

Clarify 的落地：我被问及 P 但资格不足（置信 < 门槛）或
我的置信处于 0.3–0.7 含混带 → 生成 clarify 候选 = 对该
命题的 inquire 类反问（comm_kind=clarify）。理由：本系
统的言语行为词汇只有 claim 类，clarify 没有独立的世界
语义；把它实现为「反问求证」是词汇内唯一诚实的做法，
且它确实推进信息流（对方的回答会成为我的证据）。词汇
限制如实记录，不发明世界引擎不支持的言语行为。

### 3.5 Disclosure duties 数据契约 + Withhold/Deny 衔接

duties 落在**角色配置**（不是 goal——义务不该被目标暂停
殃及，这是诊所缺口 1 的正解）：

```yaml
disclosure_duties:
  - when: <Condition>            # 主观域, 复用 conditions 词汇与 validate_subjective
    proposition: <prop>          # 必须是某 assert 类 ClaimDef 的 proposition
    targets: [agent_id, ...]     # 或 "colocated" (任一在场者)
    urgency: normal              # low|normal|high
```

校验（加载期）：when 须 subjective 合法；proposition 须
有对应 assert 类且该角色可持有其 basis；targets 须为场
景内角色。运行时语义：when 在我的视图中满足、目标在
场、且我尚未对该目标说过该命题（查我自己的 own_actions
——无状态派生，不新增簿记）→ 每 tick 生成 disclose 候
选（comm_kind=disclose，info 按 urgency 映射计价，
§3.3）。duty 候选**必生成**（与 answer 义务同级），但选
择仍归评分：性格可以压过义务，那是人物，不是 bug；压
过率由指标呈现。duty 不改世界、不改目标状态——它只是
候选来源，兼容性因此平凡：Condition 词汇表与 Goal
Schema 都不需要为它扩容（when 复用前者，它不进后者）。

Withhold/Deny 与既有参数的衔接（三者共用一条评分轴，
不新造旋钮）：
- Deny：既有 denial 类生成路径保留（sensitive 命题被问
  及且符合既有门槛）；comm_kind=deny 标注即可。
- Withhold（refuse）：既有 refuse 动作保留；新增一条
  **目标自保硬检**——生成 assert/answer 候选时，构造合
  成事件 (speak, self, claim) 用既有 _event_matches 检
  查：若它会点亮我任一目标 failure 条件的 event_occurred
  叶（「绝不说出 X」型维护目标在现行词汇中就是这样写
  的），该候选**硬否决**（不生成）并在 census 中记
  vetoed。自保是否决、不是加权——目标的条件语义不容评
  分稀释。
- 软轴沿用既有量：disclosure_threshold、trust、honesty
  全部保留现定义，只经 §3.3 的 answer/volunteer 系数分
  化进入 social 因子。secrecy 维护目标的风险定价
  （ask/search 的既有 maintenance 风险路径）扩展到
  assert：断言 P 会把 P 教给在场者、而我的维护失败叶读
  的是我感知到的世界——断言本身不直接点亮我的信念叶，
  故此处**不**新增风险项，避免把「我担心他知道」伪装成
  「我知道他知道」的主观僭越。此取舍明确记录。

## 4. C3 设计：Exploration 与统一信息价值

### 4.1 一套 Information Value（合并 B 的三处 ad-hoc）

现行 info_f 有三个互不相干的分支（命题不确定度、已搜折
扣、observe/listen 平值 0.3）。C3 将其统一为单一定义：

```
IV(a) = Σ_{x ∈ targets(a)} uncertainty(x) × relevance(x)
```

targets 与 uncertainty 按行动类型实例化（全部主观量）：
- ask(P)：uncertainty = 1 − conf(P)；这是 B 的原公式，
  保留。
- assert/answer/disclose(P → T)：uncertainty =
  ignorance(T, P)（§3.4）——即 C2 的受方估计，**同一函
  数、同一实现**（comm_candidates 与 rule_provider 共
  享 v02/info_value.py 小模块，避免两份实现漂移）。
- search(L)：uncertainty = 1 − searched_certainty(L)，
  searched_certainty = 该地点在我 own_actions/
  searched_empty_places 中的已搜状态（已搜空记 0.9——
  留 0.1 给「物件被人移动过」的世界可能性，与 B 的
  0.15 折扣同源、口径改为概率语言）；若我有该地点某
  目标物的 sighting，relevance 走该物的目标关联。
- move(L)：= 0.8 × search(L) 的 IV（沿 B 的 move×0.8，
  语义改为「移动是为搜查/接近的前置」）。
- observe/listen：targets 不可枚举（环境传感），保留平
  值 0.3 并在文档中明示其为「传感器常数」而非 IV 的特
  例——不假装统一了不可统一之物。

relevance(x) = x 关联到我 active（含 C1 口径的 eligible）
目标叶的最大优先级加权（叶命中：priority_current；
duty/话题命中：0.5×；无关联：0.1 底噪）。**fruitless
search 不完成目标**由既有评估器保证（object_found 只在
world 真找到时入视图），C3 不新增任何完成路径——任务
书 C3 验收 2 是既有语义的回归项，不是新工作。

### 4.2 生成面扩展（两个新触发，均通用）

1. **持有型叶的搜查路线**：object_possession{holder=他人}
   叶在「我无强持有信念（conf(holds:他人:物) < 0.9）且
   该物可搜」时增补 search_route——「我不确信在他手里，
   那先搜查能搜的地方」。强信念抑制是主观的、非剧情的。
2. **基线探索**：当本 tick 无任何目标叶候选且无待答义务
   时，生成 baseline search 候选：未搜过的可搜地点，
   IV = curiosity × 0.2（relevance 底噪口径），受重复惩
   罚与「已搜」折扣压制——量级刻意低于任何目标驱动行
   动（base 0.20 基准源），只在角色真闲着时浮现。
   admission_form 式第二通道由此**可能**被发现；设计上
   明确不保证、不定向（定向即剧情作弊）。诊所的正道始
   终是 C1+C2 的信息链，C3 在诊所的验收点是护士 restock
   激活**之后**搜 pharmacy（§1.3 的机制在 B 已证，C3 只
   需它在 C 栈上复现）。

### 4.3 冗余记忆落点

不新增状态：已搜集合从既有三处派生——own_actions（我的
 search 记录含地点）、searched_empty_places（agent 既有
簿记）、found_objects/object_sightings（已查获）。C3 在
SubjectiveView 上加一个只读派生属性 searched_places
（dict 地点→最近搜索 tick），供 IV 与重复惩罚共用;派生
而非存储，避免检查点再添一份可能不一致的簿记。

### 4.4 C3 改动面

新 v02/info_value.py（与 C2 共建，C3 阶段完成统一收
编）；rule_provider.py（info_f 全部改走 IV、_search_
route 触发面扩展、baseline 探索生成）；agent.py 无改
（状态派生走 view）。与 C2 的时序：IV 的 assert 分支在
C2 已先行落地（受方估计），C3 只收编 ask/search/move
分支并删除旧分支实现——收编须保持 C2 已校准量值不变，
以 C2 阶段门轨迹复跑为回归证据。

## 5. C4 设计：Plan 粒度与重规划循环控制

### 5.1 先修步评估的时间窗（根因乙，§1.4）

裁决：当前步的**完成判定改为每个 receive 都判**——
receive 时若 current_plan 有 current step，先以当前视图
判其 success（满足即 fulfilled，推进/完成计划，走既有
plan_transitions 种类）；**失败计数仍只挂在行动上**：
仅当刚执行的行动是步一致行动时才进入失败计数判定
（既有逻辑原样）。语义后果：ask 步在回答到达的那个
receive 被判完成（多 tick 插曲闭合）；失败语义不被
「等待」稀释（等待中的 receive 不产失败计数）。与 B3
既有测试的冲突面：B3 测试钉住的是「搜而未得不完成」
（完成侧，新规下依然不完成 ✓）与「连续计数失败达上限
→ blocked」（失败侧，规则不变 ✓）；钉住「单发判定」
本身的测试若存在，入 §9.2 预注册处置表逐条论证。此变
更为 C4 的地基，先行独立提交、独立回归。

### 5.2 步粒度规则（合成器与 LLM 步共同的契约）

**局部性契约**：一步的 success_condition 必须能被「该
步模板行动的结果、或这些行动直接引发的回应事件」在步
的生命内改变——即条件的引用集须与步模板的因果半径相
交。合成规则据此改写（synthesize_steps）：
- belief 叶 → 分解为 `evidence:<belief>` 步：success =
  `any[ 该 belief 叶, event_occurred{speak, 他人,
  claim∈断言该命题的类}, object_found(fact object) ]`
  （无 fact object 时去掉第三支）。belief 叶**不得单独**
  作步条件（根因甲：置信 0 即 sat 0 → 必卡）；混入
  `any` 后，叶未动而回应事件已到 → 步可完成，目标层信
  念由解释通道照旧更新（步完成 ≠ 目标完成，四层分
  离保持）。
- object 叶：保留 B 的 locate/secure 两步分解（已被仓
  库轨迹证明）。
- location 叶：保留单步（我的 move 结果直接改变它，
  局部性成立）。
- event_occurred{actor=self} 叶：单步（我自己的行动事
  件即结果）。event_occurred{他人} 叶：步条件 = 该事件
  本身（回应型插曲靠 §5.1 的每-receive 判定闭合），模
  板取 seek + 触发类行动（如向对方 assert 前置信息）。
- 失败计数规则 (c) 同步收窄：「决定性为假」只对
  object/location 类叶生效（搜遍未得、到错地方是真失
  败）；belief 类叶在置信未升时记「未遂」不记失败——实
  现上：失败计数 (c) 改为「任一**非 belief** 叶 sat=0」
  或 failure_condition 满足 或 result.ok=False。医生
  两次 ask 未得答复从此不再凑满 blocked。
- LLM 计划步：同一契约写进 context 的计划指导行 +
  运行时仅警告不驳回（LLM 步的 legacy/结构问题由 C5
  期 LLM 实验如实测，见 §8）——不在 C4 给 LLM 加新的硬
  校验，以免把度量问题修成准入问题。

### 5.3 Plan Fingerprint：语义指纹与重规划门槛

指纹（不用纯字符串相等）：对计划 P，
`steps_sig(P) = 多重集 { step_sig(s) }`，其中
step_sig = (success_condition 的**归一化叶签名集**,
 模板动词集)，叶签名 = (叶类型, 归一引用)——引用归一
化：object/belief/location/claim 取其 key，数值阈值分桶
（置信阈值按 0.25 桶），agent 引用归一为 self/other。
计划指纹 = (goal_id, steps_sig)；**相似度** =
steps_sig 的多重集 Jaccard，goal 不同直接判不相似。
目标文本、step_id、objective 措辞不入指纹（LLM 措辞抖
动不该改变指纹——这是「语义」二字的落点）。

失败记忆：agent 运行时状态 `plan_failure_memory`:
[{fingerprint, tick_failed, cause(blocked/exhausted/
abandoned), context_digest}]，上限 8 条 FIFO。
context_digest = 对**该目标 success/activation 条件引
用集**（conditions.references() 既有能力）所涉主观事
实的摘要：相关 belief 置信分桶（0.1）、holdings、
found、searched_places、自身 location——即「当年失败
时世界在我眼中的样子」，全部主观、全部可派生。

**重规划门槛**（落在 PlanManager.execute_recovery 的
replan 分支与 provider 合成入口，两处同一判定函数）：
新计划与某条失败记忆相似度 ≥ 0.8 **且** context_digest
与该记忆相同（相关事实无一变化）→ 拒绝此次 replan：
recovery 改派 suspend（reactivate_when 取失败步的
success_condition，与 B3 policy_default 的 suspend 口
径一致），落 plan_transitions 新 kind `replan_gated`
供 §八计数。「相关事实变化」包括：新证据事件命中引
用集（perceived_events 增长触及 refs）、地点/持有/已
搜集合变化、相关 belief 跨桶。仓库 keeper 的 replan 之
所以历来有效，正因其间 location 与 searched 集合持续
变化——digest 设计刻意包含这两项，使门槛**不误伤已证
明的生产性 replan**（C4 阶段门以仓库 B3 类轨迹复跑为
证：blocked→recovery→goal completed 链必须仍在）。
另设软顶：同一目标在 digest 不变期间累计 gated ≥ 3
次后，该目标的计划合成整体暂停至 digest 变化（agent
去做别的事），防「gated→suspend→恢复→再 gated」的
慢速空转。

与既有 recovery 策略的关系：retry/skip/abandon 不变；
replan 被门槛**前置过滤**（不是删除）；suspend 从策略
之一变为「无新信息时的缺省落点」。B3 的计数器
（retry_recoveries 等）语义全保留，指标可比性不断裂。

## 6. C5 盲测协议

沿 B 的场景 C 协议逐项继承，不降格：

1. **时序**：C1–C4 全部落地、阶段门全过之后，先**冻结**
决策代码并生成 sha256 清单（清单范围在冻结时重定：
C 栈的决策相关文件——v02/ 全部 *.py 中除 experiments/
audit 的度量侧外全量纳入，预计 20+ 文件，含 protocol、
runner、scheduler、world——宁宽勿窄），写入
V0.2-C_BLIND_TEST 报告头；冻结后任何决策代码改动使

2. **独立测试方**：盲测场景由未参与 C1–C4 实现的独立
一方撰写，只凭数据契约文档（V0.2-C_ARCHITECTURE 的
作者契约节 + 一个格式范例场景——沿 B 例，用仓库场
景）写纯数据（scenario JSON + 角色 YAML）；实现方在
预注册完成前不得读场景内容。
3. **场景硬性构成**（任务书 §7.2，预注册时逐项核对）：
≥3 角色（性格/私有知识互异）、≥3 目标相互依赖、跨
角色信息传递、提问**与**回答、自主探索、≥1 可失败
或被放弃的目标、≥1 计划需 blocked→recovery；地点/
物品/claims/关系全新。
4. **预注册**：跑前写定期望表（映射任务书 §7.3 十三项
验收逐条给出可观察判据与数据出处），期望表落盘后才
许首跑；判读不许事后移动门柱——**失败是合法结论**
（B 的场景 C 即以失败存档且其证据直接催生了本任务
书，C5 重蹈失败同样产出下一轮的缺口清单，不是事故）。
5. **跑法**：双 seed（42/7）× 24 tick，冻结前后各验一
次清单哈希；determinism 复验（同 seed 双跑 world_log
md5 一致）随附。
6. **诊所的定位（本节是纪律条款）**：C1–C4 期间诊所只
作**回归夹具 + 失败证据复现**：它的 B 期预注册期望
（P1/P2/P3/P9 类机制点）被 C1/C2 阶段门复用为回归判
据；在诊所上只许做三件事——跑、读、登记数据契约的
正当使用（如 §2.2 的 depends_on 声明）；**禁止**为
诊所写任何角色 ID/场景名/命题名的代码分支（任务书
§九 3 的重申），禁止以「诊所全绿」为任何阶段的结
论——阶段门的诊所判据永远与酒馆/仓库的防回归判据成
对出现。最终目标不是让诊所跑通；诊所跑通只是 C1/C2
机制成立的一个证据点。

## 8. §十一 #10 真实 LLM 实验设计（本阶段不做任何真实调用）

**实验问题**：C 栈（scheduler + comm 生成 + IV + 粒度/
指纹）在真实 LLM provider 下端到端成立否——LLM 能否产
出结构化计划、其行动结果能否进入步评估、blocked 后能
否走恢复。全 B 周期此证据为零（§1.6），这是它在最终验
收中的位置。

**实验设定（随 C5 阶段执行，设计先行冻结于此）**：
- 场景：仓库（B 场景）——rule 模式动力学已证（搜索→寻
获→完成、blocked→恢复），是唯一能把「LLM 侧差异」从
「场景本身不行」中分离出来的对照场景。不用诊所（其
rule 侧结论刚翻案，归因会缠绕），不用盲测场景（时序
在冻结后且须独立）。
- 规模：20 tick × seed 42 主跑；预算允许时加 seed 7。
决策数 ≈60，与 B 时代 llm_full20_planlayer 的 60/60
成功基线同量级。
- **预注册期望**（跑前写死，沿 B 的诚实口径）：跑满 20
tick 无崩溃；LLM 计划中结构化（非 legacy）步占比**如
实报告不设门槛**（B 栈上此数为未知，设门槛即造假压
力）；≥1 次 LLM 计划步被 step_evaluated 判 fulfilled；
若自然出现 blocked，则恢复路径须真实执行（不出现则
如实记「本跑未采样到 blocked」，#10 记部分达成——
**禁止**为凑 blocked 改场景数据造局；至多另设一个明
示的 max_attempts=1 数据变体跑并单独标注）。
- 对照：同场景同 seed 的 rule 跑（C 栈）并排呈现，与 B
时代「LLM 轨迹 vs rule 轨迹」的对照传统一致。

**后端三选项与代价**（供 Hu 拍板，开放决策 #1）：
