### 3.2 advance 语义变更（破坏性，显式标注）

provider advance 对 blocked 计划一律拒绝
（`advance_rejected_blocked`）、对条件步一律拒绝
（`advance_rejected_conditional_step`）；仅 legacy 步可由 provider
advance 推进。此变更同步写入 LLM 契约文本（单一共享常量，
一致性测试断言两后端文本一致且含 selected_goal_id / trust /
主观认知 / goal_id / recovery / blocked 字样）。

### 3.3 机制修复（门槛调试中发现）

计划合成曾被维护目标饿死：最高优先级目标是维护目标时（无
success_condition 可合成），成就目标永远得不到计划——keeper
因此从未持有计划。修复为对「最高优先级成就目标（带
success_condition）」合成。属通用机制缺口，非场景语义。

### 3.4 硬门槛：一条仓库轨迹内 blocked + 恢复 + 目标完成 —— PASS

`runs_v02/variant_b3b_seed42`（24 ticks）同一轨迹内：

- **blocked ≥1**：traveler 的 gather:goods_ready 步在 tick 6、18、
  21、24 进入 blocked（每次均为「连贯行动 + 成功条件决定性为假」
  计数满 2 次，落 step_evaluated + blocked 记录）；
- **blocked 恢复 ≥1**：tick 6、18、21 以 strategy=replan、
  source=provider 恢复（规则生成器为 blocked 计划附合成替代步，
  运行时按恢复状态机执行；旧计划 reason="replanned" 关闭）；
- **Goal 完成 ≥1**：keeper 的 find_missing_key 于 tick 3 完成
  （goal_changes 落 goal_completed）；keeper 的计划亦于 tick 4 以
  result_driven:secure:warehouse_key 完成（plan_completed，
  skipped=0）。
