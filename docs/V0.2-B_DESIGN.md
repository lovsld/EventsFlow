## 0. 执行摘要

外部审查的总判定（V0.2-A 架构成立、三个核心问题 + 一个 P0）经逐条代码核实：**14 条指控中 12 条属实、2 条部分属实、0 条不准确**（明细见 §1）。P0（Action 成功被误认为 Plan Step 完成）已构造复现成功。

V0.2-B 的设计主线只有一句话：**把「场景语义」从代码里全部搬进数据，把「完成」从行动执行层全部搬进条件评估层。** 具体是三台引擎 + 一层能力：

| 组件 | 职责 | 取代现状 |
|---|---|---|
| **Scenario Capability**（B1） | 场景的全部静态语义（地点/物品/能力/命题/台词）以数据形式声明；决策层只读当前运行实例的 Scenario Definition | rule_provider 的角色分支与自备 ADJACENCY、context_builder 的 back_room/owner 写死、prediction 的 back_room 写死、`_interpret` 的 claim 表、plan_steps 的酒馆步名表 |
| **Goal Engine**（B2） | Goal 的激活/优先级/进度/完成/失败由 GoalEvaluator 对**结构化条件**求值，与 Plan 步骤数彻底脱钩 | plan_manager 的 `_sync_goal_*` 标签联动（progress = 步骤比例、计划完成 = 目标完成） |
| **Plan Engine**（B3） | PlanStep 携带结构化 success/failure 条件；StepEvaluator 对**行动结果内容 + 观察事实**评估步骤；blocked 有五种受 PlanManager 管辖的恢复策略 | plan_steps 谓词表（按动词类型判完成）、provider advance 一键解阻+跳步 |
| **Generic Candidate Generator**（B1，rule 路径） | 候选从「目标未满足子条件 × 场景能力 × 本人信念」生成，效用评分因子显式、可审计落盘 | rule_provider 中按角色 id 写死的候选生成 |

阶段顺序按审查 §八：B1 场景能力 → B2 Goal Engine → B3 Plan Engine → B4 三场景评测（场景 C 在 B3 后冻结决策代码才设计）。每阶段的改动文件、测试、轨迹验收物与 §十验收清单的对应见 §7、§8。

### 1.1 P0 复现记录（设计阶段实证，非单元测试）

在不改任何代码的前提下，用项目 venv 对实际模块做内存构造（脚本仅调用公开函数）：

```
step_fulfilled("press_for_evidence", {"type":"search","target_location":"back_room"},
               True, agent_loc="back_room", owner_loc="tables")  →  True
   # found=[] 无从传入：step_fulfilled 的签名里没有结果内容参数
step_fulfilled("find_letter_source", {"type":"observe"}, True, ...)  →  True
   # 任意一次成功的 observe 即「完成」了查清信件来源这一步

PlanManager._advance ×2 于 PlanState(goal="find_missing_key", steps=["go_storage","search_storage"])
   → goal.progress: 0.5 → 1.0, goal.status: active → completed
   # 整个调用链中不存在世界状态：搜索没找到钥匙这一事实无处进入判定
```

结论：P0 不是边界情况而是当前完成语义的定义本身——**完成 = 指针走到了末尾**。B3 的全部设计都围绕把这个定义换掉。

| D3 | 不再加角色/剧情 if/else | 代码评审口径：B1 起，providers/、agent.py、plan_*、goal_* 中不得新增以 character_id、claim 字面量、object id、location 字面量为键的分支；场景差异只能来自 Scenario Definition 与角色配置数据 |

| D10 | 机制须有真实轨迹证明 | §十的轨迹类硬指标（Goal 完成 ≥1、优先级行为变化 ≥1、blocked 触发 ≥1、blocked 恢复 ≥1）分别指定了产生它们的指定运行（§7 各阶段「轨迹验收物」），不靠单测凑数 |

## 3. B1 设计：统一 Scenario Capability

### 3.1 Scenario Definition 数据契约

现状：世界静态结构已是数据（`world_config.DEFAULT_WORLD` / 场景 JSON），但只含 locations/scenery/adjacency/objects{holder, location, seen_by}/ambient，且 objects 没有能力属性、没有命题声明。B1 把它扩展为完整的 **Scenario Definition**，一份 JSON（或等价 dict）描述一个场景的全部静态语义。WorldEngine 继续消费它，新增的决策侧消费者（Broker / ContextBuilder / Prediction / CandidateGenerator / StepEvaluator）消费同一份实例。

```jsonc
{
  "scenario_id": "tavern_letter",          // 必填，写进 run_meta
  "version": 1,
  "locations": ["bar", "tables", "door", "back_room", "outside"],
  "adjacency": { "bar": ["tables"], "...": ["..."] },
  "scenery":   { "back_room": ["drawer", "ledger_shelf"], "...": [] },
  "objects": {
    "anonymous_letter": {
      "location": "back_room",             // 客观初始位置（null = 被持有/未知）
      "holder": "owner",                   // 登记持有者（null = 无人）
      "searchable": true,                  // 能否被 search 发现
      "movable": true,                     // 位置可否因行动改变（为 take/give 语义预留，B 版不实现转移）
      "displayable": true,                 // 能否被 show
      "on_found": "inspect",               // 发现时处理: inspect=只读知悉 | acquire=搜查者取得持有
      "fact_belief": "anonymous_letter_exists",
      "reveals": [                          // 发现/被展示时，物品内容作为证据来源给出的命题
        {"belief": "mayor_embezzled", "reliability": 0.6}
      ]
    }
  },
  "claims": {                              // 话语命题类别（见 §3.5）
    "mayor_hint":   {"proposition": "mayor_embezzled", "stance": "assert",
                     "base_reliability": 0.45},
    "denial":       {"stance": "deny"},    // 否认的对象 = 被问及的命题，运行时由 pending_question 决定
    "letter_question": {"proposition": "anonymous_letter_exists",
                        "stance": "inquire", "sensitive": true}
  },
  "speech_lines": {                        // 纯内容包：只决定「怎么说」，不决定「是否说/说什么立场」
    "mayor_hint": ["{name}：（压低声音）镇上那笔公共资金……数目好像对不上。"]
  },
  "ambient": [["rain_starts", null, "…"], ["..."]]
}
```

字段规则：

- `objects.*` 的能力属性缺省：searchable=false、movable=false、displayable=false、on_found="inspect"、reveals=[]。Resolver 的 search/show 判定改为读这些属性（search 只发现 searchable 且客观位置 == 搜查地的物品——现行为对信等价；show 要求 displayable 且 holder == 行动者——现行为等价）。
- `fact_belief`：发现该物品 ⇒ 以 direct_observation 证据写入此命题（reliability 1.0）。取代 agent.py found 分支中写死的 anonymous_letter_exists。
- `reveals`：发现（inspect/acquire）或被 show 时，物品作为来源（source = object id）以 testimony 证据写入所列命题——物品内容的可信度由 reliability 声明，而不是由代码写死 0.6/0.55。取代 found 分支与 show 分支中的 mayor_embezzled 写入。
- `on_found = "acquire"` 时，Resolver 在 search 成功发现后把该物品的 holder 改为搜查者、location 置 null（世界侧唯一新增行为，数据驱动；酒馆信为 inspect，行为不变）。这是 §4 中 object_possession 类目标（如仓库钥匙）能成立的前提。
- 校验：Scenario Definition 在装载时做 schema 校验（新模块 `v02/scenario.py` 的 Pydantic 模型）：地点/物品/命题引用不存在 → 启动失败并点名。场景数据错误不许跑到一半才炸。

### 3.2 Capability Registry

职责：给定 Scenario Definition 与 Agent 的**当前位置和同场者**，计算「环境在此处允许哪些行动」——即 available_actions 的唯一来源，取代 context_builder 中写死的 back_room/owner 分支。

接口（新模块 `v02/scenario.py`）：

```python
class CapabilityRegistry:
    def __init__(self, scenario: ScenarioDefinition): ...
    def available_actions(self, *, location: str,
                          colocated: list[str],
                          held_objects: list[str]) -> list[dict]:
        """与现 DecisionContext.available_actions 同形（{type, target?, target_location?, object?}）。
        规则（全部数据驱动，无场景字面量）：
        - move: 当前地点的 adjacency 邻居（来自本实例 scenario，非模块级常量）
        - speak/ask/confront: 同场每个他人
        - search: 当前地点存在 searchable 物品（客观）或 scenery 声明了
          searchable_scenery（见下）时提供，target_location = 当前地点
        - show: 对每个 displayable 且 holder == 本人的物品 × 每个同场者
        - observe/listen/work/refuse/wait: 恒提供"""
```

设计要点：

- **能力 ≠ 知识**。search 在「有可搜之处」时提供给所有人（知道房间里有抽屉是结构知识，和今天 search 只在 back_room 提供给所有人同理）；某个物品具体在不在、值不值得搜，由候选生成与信念决定，不由 Registry 决定。Registry 读客观结构是正当的——它等价于今天的 available_actions 口径，不构成信息泄漏（泄漏检查仍由既有隔离测试与审计 M2 把守：行动「可用」不等于角色「知道结果」）。
- scenery 的可搜性：给 scenery 条目一个可选的对象化写法 `{"id": "drawer", "searchable": true}`（字符串条目视为不可搜的纯景物）。酒馆迁移：back_room 的 drawer 标 searchable（如此 search 在后屋提供的原因是「有抽屉」而非「地点名叫 back_room」）；仓库场景同理标 crates/shelves。
- `held_objects` 来自 Agent 状态新增的 `holdings` 列表（本人持有物，由本人行动结果维护：初始 = profile.possessions 中与 scenario objects 的交集 + acquire 事件增减）。取代 context_builder 中「owner + 信念」式的 show 判定。
- Registry 同时向 Candidate Generator 与 StepEvaluator 提供谓词求值所需的场景事实查询（object 的属性、地点邻接），是三者共享的唯一场景入口。

### 3.3 谓词词汇表（封闭集合）

Goal 的 activation/success/failure 条件、PlanStep 的 success/failure 条件、suspend 的再激活条件，全部用同一套结构化谓词表达。**词汇表是封闭的**：新增谓词类型 = 改代码 + 改本文档 + 加测试，不许场景数据自创类型。每个谓词标注求值域：

- **subjective**：只读 Agent 本人状态（信念/持有/关系/本人位置/本人感知史）。**决策路径（GoalEvaluator、StepEvaluator、Candidate Generator）只许用 subjective 谓词**——这是 D6 的落点：完成判定永远基于角色自己的认知，传闻永远不会被当成客观事实（传闻只能以 belief_threshold 的低置信形态进入）。
- **objective**：读世界快照。只许用于实验度量与场景级断言（如「钥匙客观上已被找到」），**不许出现在任何驱动行为的条件里**。同名谓词在两种域下是两个求值函数，条件数据里必须显式写 `"domain": "objective"` 才走客观求值，缺省 subjective。

| 谓词 type | 参数 | 满足度（0–1，布尔谓词为 0/1） | 语义（subjective 域） |
|---|---|---|---|
| `object_possession` | object, holder（"self" 或角色 id） | 0/1 | holder=self：object ∈ 本人 holdings；holder=他人：本人有该人持有该物的 direct 类证据（见过 show / 亲眼所见）形成的信念 `holds:<holder>:<object>` ≥ 0.9 |
| `object_at_location` | object, location | 0/1 | 本人有该物品位于该地点的 direct_observation 证据（自己搜到/亲眼见），或本人正持有且身在此地 |
| `object_found` | object | 0/1 | 本人至少一次以 search 发现过该物品（本人行动结果记录） |
| `belief_threshold` | belief, min_confidence, min_source_tier（可选） | clamp01(conf / min_confidence)；若声明 min_source_tier 而现有最高证据等级不足，满足度 ×0.5 且不算「满足」 | 本人对命题的置信达到阈值（可选：且证据等级达到要求，如必须亲历） |
| `agent_at_location` | agent（"self" 或角色 id）, location | 0/1 | self：本人当前位置；他人：本人最近一次感知到的该角色位置（感知史）与之相符 |
| `event_occurred` | type?, actor?, target?, claim?, object?, within_ticks?（可选） | 0/1 | 本人感知史（perceived events + utterances_heard + 本人行动记录）中出现过匹配事件；within_ticks 限定近 N tick 内 |
| `trust_threshold` | other, min_trust | clamp01(trust / min_trust) | 本人对 other 的信任达到阈值 |
| `goal_status` | goal（key）, status | 0/1 | 本人另一个目标的当前状态（用于目标间激活链） |

组合子：条件 = 谓词 | `{"all": [条件…]}` | `{"any": [条件…]}` | `{"not": 条件}`。满足 = 满足度 ≥ 1.0（布尔组合：all 取 min、any 取 max、not 取 1−x；「满足」判定对 all/叶谓词要求 ==1，对 belief_threshold/trust_threshold 这类连续谓词要求其归一化满足度 ≥1 即达到阈值本身）。

求值者与时机：谓词求值器是单一纯函数模块（`v02/conditions.py` 新建）：`evaluate(condition, view) -> (satisfaction: float, leaf_report: list)`，view 是求值域对应的只读视图（subjective view = Agent 状态 + 本人最近行动结果 + 本人新感知事件）。GoalEvaluator、StepEvaluator、Candidate Generator 三者共用它——同一个条件在三个地方求值结果必须一致，这是「完成语义只有一个定义」的工程落点。leaf_report 供审计落盘（哪个子条件满足/未满足，一目了然）。

### 3.4 角色与目标配置契约

角色配置（characters*/<id>/*.yaml）保持四件套格式，goals.yaml 扩展可选字段（全部缺省向后兼容）：

```yaml
goals:
- key: find_missing_key
  desc: 找回失踪的仓库钥匙
  weight: 0.85                      # = priority 基础值（沿用既有字段名）
  kind: achievement                 # achievement | maintenance（缺省 achievement）
  activation_condition:             # 缺省 = 开局即激活
    type: belief_threshold
    belief: key_missing_this_morning
    min_confidence: 0.8
  success_condition:                # achievement 必填（迁移期可缺，缺则该目标永不由评估器判完成，见 §4.6）
    type: object_possession
    object: warehouse_key
    holder: self
  failure_condition:                # 可选
    type: event_occurred
    type_: confront                   # (示意: 被东家质问) — 实际字段以 §3.3 谓词参数为准
  priority_rules:                   # 优先级动态（见 §4.4），可选
  - when: {type: belief_threshold, belief: key_missing_this_morning, min_confidence: 0.95}
    delta: +0.15
    once: true
```

- `kind: maintenance` 的目标（保护酒馆、避免卷入、维护荣誉类）没有 success_condition：它们永不「完成」，只有 failure_condition 定义其失败；进度在指标中单独口径处理（§6）。这是对酒馆目标的诚实建模——现状九个目标里至少四个本质是维持型，硬给它们编造完成条件等于新一轮剧情造假。
- private_knowledge、personality、principles、disclosure_threshold 维持现状格式。disclosure_threshold 在新设计中被通用化使用（§3.5 的披露门控），不再是 owner 专属字段的实质（它本来就在每个角色的 profile 里）。
- 角色配置**不许**再出现指向具体其他角色 id 的行为字段；角色间差异只来自数值（人格/门槛/权重）与文本（identity/principles/初始信念）。

### 3.5 话语与 Claim 契约：`_interpret` 的替代机制

原则：**一句话的「内容」由场景数据声明（claim 类别 → 命题），「对听者的作用」由通用规则从听者自己的信念、人格、关系派生。** 解释层从此不设立计划、不写角色专属分支。机制分三条通用通道，全部在 agent 的感知解释路径执行，与 Provider 无关（LLM/rule 同等适用——这一点保持现状的正确部分）：

**通道一：命题证据（assert 类 claim）**。听到 claim C（proposition=P, stance=assert）→ 经既有证据机制写入信念 P：source_type=testimony、source=speaker、event_id 去重，reliability = `C.base_reliability × trust_factor(speaker)`，其中 trust_factor = 0.4 + 0.6 × trust_in(speaker) ∈ [0.4, 1.0]。置信度的合并、升级、corroborate 全部由 V0.2-A 的证据重算负责——「两个独立说话人说同一件事比一个人说更可信」是重算规则的涌现性质，不再需要 mayor 三分支写死 0.45/0.5。
未在场景 claims 中声明的 claim → 只记情节记忆，不产生信念效应（安全缺省；LLM 自创 claim 因此不会凭空造信念）。

**通道二：言语行为效应（与 claim 内容无关，只看动词与指向）**。
- ask/confront 指向本人 → arousal += 0.25 × caution 本人 × 重复衰减（同一说话人同类询问第 n 次，系数 1/n——现 investigation_probe 分支的衰减机制本就是通用的，保留）；若被问及的命题在场景 claims 中标 `sensitive: true`，suspicion 另加 0.2 × 衰减。
- 本人发言被 refuse → 对说话人 trust −0.05（现 _perceive_event 已有此通用条目，保留）。
- show 事件 → 走物品通道：被展示物品的 fact_belief 以 direct_interaction 写入、reveals 以 testimony（source=物品）写入、trust(展示者) +0.1（现行为的通用化，数值保留）。
- search 事件被同场看到 → suspicion +0.1（现行为，通用，保留）。

**通道三：矛盾推断（deny 类 claim）**。听到某人对命题 P 给出 deny，而本人持有 P 且 confidence ≥ 0.5 → 以 inference 写入信念 `conceals:<speaker>`（desc 由 claim 与 P 生成），reliability = 0.5 + 0.3 × (本人对 P 的 confidence − 0.5) × 2，钳制 [0.5, 0.8]；suspicion += 0.15。取代现 denial 分支的 owner_hiding_something 写死 key——信念 key 变成通用模式，酒馆轨迹中该信念将以 conceals:owner 出现（轨迹差异点，记入 §7.5 重钉说明）。

**发言侧的披露门控（通用，取代 owner 专属逻辑）**：当说话人被问及命题 P（pending_question 指向 P）时，其候选生成（§3.6）按统一规则产出三类回应候选：如实陈述（assert 自己所信）、否认（deny）、回避（refuse/转移话题），评分由 trust_in(提问者) 与本人 disclosure_threshold、人格 caution 决定——trust 越过门槛则如实类加分，否则否认/回避加分。现 owner 的「信任够了暗示一点、不够就否认」是这条规则在酒馆参数下的实例，行为等价迁移。

**解释层不再做的事**：不设立/替换计划（计划的来源见 §3.6 合成器与 §5）；不按角色 id 分支；不按 claim 写死信念 key（key 来自 claims 声明的 proposition 与通用模式 conceals:<speaker>）；物品发现的认知效应走 objects 声明（fact_belief/reveals），不再有 anonymous_letter 专支（found 分支与 show 分支一并删除）。

### 3.6 Generic Candidate Generator（rule 路径）与效用评分

rule provider 重写为**通用候选生成 + 显式效用评分**，LLM 路径不变（模型在 available_actions 内直选——V0.2-A 审查已确认维持该形态）。生成器只读 DecisionContext（含 B1 新增的 scenario 视图与本人信念）+ 本人目标/计划状态，候选来源四类：

1. **目标驱动候选**：取当前选定目标（§4.4 的优先级序第一位 active 目标），对其 success_condition 的每个**未满足叶谓词**，按谓词类型套用通用候选模板：
   - `object_found / object_at_location / object_possession(object)` → search 候选（地点：本人相信物品可能在的地点集——来自本人关于该物品位置的信念/感知史；无信念时为全部有 searchable 景物的地点）+ 向这些地点的 move 候选 + 向同场者 inquire 该物品的 ask 候选（claim = 场景中 proposition == 该物品 fact_belief 的 inquire 类 claim；无声明时用通用 topic 询问，不带 claim）；
   - `belief_threshold(P)` → 向同场者的 ask/speak 候选（claim = proposition == P 的 assert/inquire 类）、observe/listen 候选、（若 P 关联某物品）search 候选；当本人对 P 的 confidence 已 ≥ 0.8×阈值且人格 impulsiveness 高时，confront 候选（摊牌/指控类 claim 由场景声明）；
   - `agent_at_location(self, L)` 未满足 → 向 L 的最短路 move 候选（邻接来自本实例 scenario）；
   - `event_occurred(...)`（如「质问某人」型）→ 对应的发言候选；
   - maintenance 目标不产生正向候选，只产生**风险修正**（见下 SocialCost/RiskCost）。
2. **计划步候选**：当前计划步的 action_candidates 模板（§5.1）实例化为具体行动——天然获得 PlanConsistency 加分。
3. **社交/情境候选**：回应 pending_question 的三类回应（§3.5 披露门控）、对同场者的 greeting 类发言（claim 由场景 speech_lines 的社交类提供，可缺省为无 claim 的 speak）。
4. **基线候选**：observe / listen / work / wait（work 的 topic 来自角色配置的 routine 声明——新增可选 profile 字段 `routine: {verb: work, topic: tend_bar}`，把现 owner/merchant 的 work 分支数据化；无声明则只有 observe/listen/wait）。

**效用评分**（审查 §4.5/§6.5 公式在本系统的落地；每项归一化到 [0,1] 或注明界，权重由人格数值派生，全部系数写在生成器常量表中并可在实验报告中复算）：

```
Utility(a) = wG·GoalAlignment(a) + wI·InformationValue(a) + wP·PersonalityPreference(a)
           + wE·EmotionInfluence(a) + wC·PlanConsistency(a)
           − wR·RiskCost(a) − wS·SocialCost(a) − RepetitionPenalty(a)
```

- GoalAlignment：a 命中选定目标某个未满足叶谓词的候选模板 → 1.0；命中次优先目标 → 0.5；命中已满足条件/无关 → 0。**这是审查 §4.5 的核心要求：改目标优先级必须能改行为**（B2 用对照运行验证，§7）。
- InformationValue：a 是 search/observe/listen/ask 且其目标命题/物品在本人信念中缺失或低置信 → 与不确定性成正比（1 − conf）；已知透了 → 趋 0。
- PersonalityPreference：把现 rule 评分中的人格项正规化保留（curiosity→search/ask，sociability→speak，caution→observe，impulsiveness→confront/move 的既有系数形态，逐项在代码常量表中注明来源）。
- EmotionInfluence：suspicion 高 → search/confront 加分（现 0.5·suspicion 项的正规化）；arousal 高 → 行动类加分、wait 减分。
- PlanConsistency：a 命中当前计划步 action_candidates → +STEP_ALIGNMENT（沿用现 0.35 量级，作为效用的一项而非外挂）。
- RiskCost：a 可能触发任一 maintenance 目标的 failure_condition（如对他人 show 敏感物品、assert 敏感命题给低信任者）→ 按该目标 priority 加权扣分；confront 对低信任对象 → 按 caution 扣分。
- SocialCost：对 trust 低者 assert 本人无证据的命题（吹牛类）按 honesty 人格扣分——**这给 honesty 维度安排了第一个真实读点**（V0.2-A 遗留的未生效维度）；refuse/deny 对高信任者扣分。
- RepetitionPenalty：沿用现有的按 action_counts 的递减（发言类 0.22/次、其他 0.05/次）。
- 随机性：argmax 前加 seeded RNG 抖动，上界 0.18（沿用现值），抖动在评分之后、种子由 (run seed, character seed_offset, tick) 决定，PYTHONHASHSEED 无关性靠 sorted() 枚举维持（现纪律）。

**可审计**：每条决策的 record 新增 `candidate_scores`：前 5 名候选的 {action_sig, total, factors{goal, info, personality, emotion, plan, risk, social, repetition, jitter}} 与最终选择，落入决策审计记录（persistence 需加一个可空 JSON 列；旧 run 读不到此列时指标报 None，沿用既有诚实口径）。reasoning_summary 继续保留人读摘要。

**计划合成（rule 路径）**：当选定目标没有服务于它的计划时，生成器在产出候选的同时经 plan_update 通道提出合成计划：步序列由 success_condition 的叶谓词按「先定位、后处置」的固定谓词序生成（object 类：[locate 步（success = object_found 或 belief 达标）, act 步]；belief 类：[gather 步（success = 该叶谓词）]；location 类：[move 步]），每步携带 success_condition（= 对应叶谓词）、action_candidates（= 该叶的候选模板）、默认 retry_policy（§5.5）。合成计划的 goal_id = 选定目标 key——**计划与目标的关联从产生源头就是结构化的**，不再靠标签巧合。LLM 路径的计划仍由模型经 plan_update 提出（步为自由文本时按 §5.7 的 legacy 步处理）。

### 3.7 配置贯通（Threading）设计

一个运行实例只有一个 Scenario Definition 对象，由 runner 在组装时创建（来自 world_config 参数 / scenarios/*.json / DEFAULT_WORLD），并**显式注入**：WorldEngine（已有）、EventBroker（新增构造参数 world_config，build_perception 的邻接改读实例）、Scheduler→Agent（agent 持有 scenario 引用：found/reveals 解释、StepEvaluator、GoalEvaluator 的场景查询）、ContextBuilder（build_context(agent, perception, registry) 签名扩展，available_actions 来自 Registry）、PredictionEngine（found 预期改为：搜查地点存在 searchable 物品且本人尚无「该地已搜空」的信念时，按本人对该物品位置的信念给出；adjacency 读实例）、RuleProvider（经 DecisionContext 的 scenario 视图消费：context 新增 `scenario` extra = {locations, adjacency, objects 的**结构**信息（id + 能力属性，不含客观位置/holder——那是世界事实，角色只能经信念知道；Registry 侧的 available 计算在 context 构建期已完成，provider 只看 available_actions 与本人信念）})、plan_steps 的过渡期消费者（B3 删除前，其 ADJACENCY 改为由 agent 在 stashing step check 时传入实例邻接——或直接在 B1 把 step_fulfilled 的邻接参数化）。

## 4. B2 设计：Goal Engine

### 4.1 Goal 完整字段（protocol.Goal 扩展，全部新增字段有缺省、旧数据可载入）

| 字段 | 类型 | 说明 |
|---|---|---|
| key / desc / weight | 沿用 | weight 即 priority 基础值（改名只在文档层称 priority_base，不动数据字段名，避免无谓迁移） |
| kind | `achievement \| maintenance`，缺省 achievement | maintenance 无 success_condition |
| status | `inactive \| active \| paused \| completed \| abandoned \| failed` | 在现有四值上新增 inactive 与 failed（审查 §4.4 状态机）；completed/abandoned/failed 为终局 |
| activation_condition | 条件（§3.3）\| null | null = 开局 active（兼容现状）；非 null 时初始 inactive |
| success_condition | 条件 \| null | achievement 的完成判据；只许 subjective 谓词 |
| failure_condition | 条件 \| null | 满足 → failed（与 abandoned 严格区分：failed 是条件触发，abandoned 是主体选择） |
| priority_current | float | 运行时优先级（初始 = weight），由 §4.4 的规则调整；weight 永不改 |
| priority_rules | list[{when, delta, once}] | 来自配置（§3.4） |
| progress | float 0–1 | 由 §4.3 的条件满足度计算；maintenance 目标恒为 null（序列化为 null，指标分开统计） |
| commitment / created_at / deadline | 沿用 | commitment 语义保留为「目标层承诺」（影响 §5 的计划替换门控取值来源：计划 commitment 初始值取所属目标 commitment）；deadline 本版仍只记录不触发（沿用 V0.2-A 的如实标注，不在本版编造到期语义） |

### 4.2 GoalEvaluator：职责与求值时机

新模块 `v02/goal_engine.py`，纯状态组件（与 BeliefManager / PlanManager 同级），接口：

```python
class GoalEvaluator:
    def evaluate(self, agent, tick: int, cause: str) -> list[GoalChange]:
        """对 agent 的每个非终局目标依次判定：
        inactive → active（activation_condition 满足）
        active/paused → failed（failure_condition 满足，先于完成判定）
        achievement active/paused → completed（success_condition 满足）
        active ⇄ paused（§4.5 的暂停规则）
        priority_current 更新（§4.4）
        progress 重算（§4.3）
        每次变化产出一条 GoalChange（kind: activated/goal_progress/
        goal_completed/goal_failed/goal_paused/goal_reactivated/
        priority_change/goal_abandoned，带 before/after 与 leaf_report），
        agent 将其排入 chain updates 落 goal_changes 表（表已存在，扩 kind 值）。"""
```

求值时机（钉死在决策循环里，审查 §七数据流的落点）：

1. **receive() 末尾**：本 tick 的全部信念/信任/持有变化（预测误差路径 + 结果事实摄入 + 感知解释）落定之后、decide() 之前调一次（cause="perception"）。这是主求值点：目标状态永远在决策前是新鲜的。
2. **计划事件之后**：计划完成/放弃不再直接写目标（删除 `_sync_goal_*`），但计划状态是某些 goal_status 谓词与暂停规则的输入，故在 decide() 内 PlanManager.apply_update 之后补调一次（cause="plan_event"），保证同 tick 内连锁变化（如计划放弃 → 目标暂停判定）不延迟一个 tick。
3. 初始化：run 开始时对全部目标调一次（cause="init"），activation_condition 已满足的目标在此激活并落行——「开局即满足」与「从未激活」从此可区分（修 §1 #14 的一半）。

求值顺序内的优先级：failed 先于 completed（同一 tick 两者都满足时判 failed，理由：失败条件通常是「坏事已发生」，不能被同 tick 的完成掩盖；此规则写进测试）。

### 4.3 Progress 的独立计算口径

progress 只来自 success_condition 的满足度，与任何计划的步数无关：

- 把 success_condition 展平为叶谓词集合（all = 全部叶、权重均等；any = 取满足度最大的叶作为整体满足度；not 叶按其满足度计）。
- achievement 目标：progress = all 时各叶满足度的均值；any 时最大叶满足度。叶满足度按 §3.3 表（belief_threshold 为 conf/θ 钳制，trust_threshold 同理，其余 0/1）。
- progress 只在「变化 ≥ 0.001」时落 goal_progress 行（防刷表），但终局判定用未取整值。
- 计划走完而条件未满足 → progress 停在条件满足度处、目标保持 active：这正是审查 §4.3 钥匙例子的期望行为（去了仓库、搜了仓库、没找到：progress 只有 agent_at_location 类子条件得分，object_possession 仍为 0）。

### 4.4 优先级：静态基础 + 事件驱动动态

- 排序口径：一切「选哪个目标」的场合（context 呈现序、生成器选定目标、rule 的 selected_goal_id）统一用 **priority_current** 降序（同分以 key 字典序定序，保证确定性）。selected_goal_id 从此 = 生成器实际服务的目标，贴标签问题（§1 #8 副作用）随之消失。
- 变化来源只有两个：① 配置的 priority_rules（条件边沿触发：when 条件由假变真时施加 delta，once=true 只施加一次，once=false 则在条件为真期间保持、转假时撤除——实现取「重算式」：priority_current = clamp(weight + Σ 当前生效规则的 delta)，无状态漂移）；② 目标状态变化的连带（目标被暂停期间不参与排序；新激活目标即刻参与）。
- 每次 priority_current 变化落 priority_change 行（before/after + 命中的规则下标/原因）。**不引入** LLM 或 rule 对优先级的自由修改（沿用 V0.2-A 不采纳项：目标不许每 tick 随意变）。
- 审查 §4.5 的验证实验（同角色双目标、调换优先级 → 行为合理变化）在 B2 验收中以**受控对照运行**实现：同一场景同一 seed，只改一个角色两个目标的 weight，断言其决策的 selected_goal_id 分布与首个目标驱动行动显著翻转（§7 B2 轨迹验收物）。

### 4.5 Goal ↔ Plan 的稳定关联

- `PlanState` 新增 `goal_id: str | None`（保留既有 `goal` 字段作人读标签，过渡期内两者并存；新代码一律以 goal_id 为准）。计划来源与 goal_id 的填法：
  - 合成器计划（§3.6）：goal_id = 所服务的目标 key（必然合法）；
  - provider plan_update 提出 replace 时：PlanUpdate 新增可选 `goal_id`，经与 selected_goal_id 相同的归属校验（不属于本人目标集 → 该 plan_update 判无效并记录）；缺省时：若当前计划有 goal_id 则继承，否则 None；
  - 解释层：不再设立计划（§3.5），此来源消失；
  - legacy 自由标签计划（LLM 自由文本步等）：goal_id=None，标记 **unlinked**。
- 联动规则（取代 `_sync_goal_*` 的全部职责）：**没有任何计划事件直接改目标状态**。计划只是 GoalEvaluator 的输入之一：goal_status 谓词可读计划状态；暂停规则（下条）读计划归属。目标 progress/completion 只由条件求值产生（§4.3/§4.2）。
- 暂停规则（确定性，写进 evaluate）：active 目标 G 有一个未完成的 linked 计划 P，而 P 被另一个目标的计划替换/放弃 → G 在下一次 evaluate 时若仍 active 且其 success 未满足 → paused（reason 记录来源计划事件）；G 重新获得 linked 计划或成为 priority 序首位且当前无计划时 → 由合成器接手并在 evaluate 中 paused → active（goal_reactivated）。这保留了 V0.2-A 单计划运行时下「换计划即暂停旧目标」的可观察语义，但判定权归 GoalEvaluator 且有条件依据。

## 5. B3 设计：结果驱动 Plan Engine

### 5.1 四层完成语义（P0 的正面定义）

| 层 | 定义 | 判定者 | 输入 | 审计 |
|---|---|---|---|---|
| Action 成功 | Resolver 接受并执行了行动 | World/Resolver（现状） | intent | execution_result.ok / reason |
| Plan Step 完成 | 该步声明的 success_condition 对（行动结果内容 + 行动后本人认知）求值为满足 | **StepEvaluator**（新） | action_result 全量（含 found）、本人新信念/持有、本步条件 | step_evaluations（§5.6） |
| Plan 完成 | 全部步完成（含以 skip 方式越过的步——skip 只表示「不再尝试这一步」，见 §5.5）或计划被以完成语义关闭 | PlanManager（状态机） | 各步 status | plan_transitions |
| Goal 完成 | success_condition 满足 | GoalEvaluator（§4） | 本人认知状态 | goal_changes |

四层互不蕴含：Action 成功 ⇏ Step 完成（P0）；Step 全完成 ⇒ Plan 完成，但 ⇏ Goal 完成（§4.3）；Goal 也可在计划之外完成（条件被其他途径满足时，GoalEvaluator 照样判完成，计划随后被自动收尾——evaluate 时发现 linked 计划的目标已 completed → 计划以 kind=goal_already_completed 关闭）。

### 5.2 PlanStep 结构与 StepEvaluator

```python
class PlanStep(BaseModel):
    step_id: str                      # 计划内唯一，如 "find_missing_key:1:object_found"
    objective: str                    # 人读目标（合成器由条件生成；LLM 步为其原文）
    action_candidates: list[dict]     # 行动模板 [{type, target?, target_location?, object?, claim?}]
                                      # 模板字段可缺省 = 该字段任意；用于一致性判定与生成器加分
    success_condition: dict | None    # §3.3 谓词条件；None = legacy 步（§5.7）
    failure_condition: dict | None    # 满足即本步失败一次（不等重试耗尽）
    retry_policy: RetryPolicy         # {max_attempts: int = 2, on_exhausted: "replan"}
    status: Literal["pending","active","fulfilled","failed","skipped"] = "pending"
    attempts: int = 0
```

```python
class StepEvaluation(BaseModel):
    fulfilled: bool                   # success_condition 满足
    failed: bool                      # 本次计为一次失败（§5.4 的精确定义）
    reason: str                       # 如 "object_not_found" / "result_not_ok" /
                                      # "condition_unmet:object_possession" / "fulfilled"
    leaf_report: list[dict]           # success/failure 条件的子条件求值明细
```

- 求值者：新模块 `v02/plan_evaluator.py · PlanStepEvaluator`，只依赖 conditions.py 的求值器 + 本人状态，**不含任何地点/角色/物品字面量**（审查 §六的落点：PlanManager 与 Evaluator 都只见条件与结果）。
- 求值时机：agent.receive() 内，顺序钉死为：① 评估上一决策的 prediction（现状）；② **摄入行动结果事实**（found 物品 → fact_belief/reveals 证据 + holdings 更新——从现 found 分支通用化而来，移到此处使第 ③ 步能看见）；③ StepEvaluator 评估 pending step（输入：stash 的 step 快照、本次 action_result、当前本人状态、新感知事件）；④ GoalEvaluator.evaluate（§4.2 时机 1）；⑤ 解释新感知事件（utterances 等）；⑥ GoalEvaluator 补评一次（感知可能改变目标条件——与 §4.2 时机 1 合并实现为 receive 末尾统一调用，③④⑤ 的相对次序以本条为准，B3 实施时以测试钉住）。
- 一致性判定（供生成器 PlanConsistency 与审计 M1 的新口径）：action 与某步一致 ⇔ action 匹配该步任一 action_candidates 模板（字段级匹配，语义同 context_builder.action_is_offered）。plan_steps.py 的步名谓词表在 B3 删除，M1 改按此定义计算（数值口径变化在 B3 报告中与旧值并列说明，不许混报）。

### 5.3 PlanState v2 与状态机

PlanState 变更：steps: list[PlanStep]（§5.7 给迁移规则）；新增 `goal_id`（§4.5）、`blocked_info: {reason, since_tick, step_id} | None`；status 集合扩为 active / blocked / suspended / completed / abandoned（suspended 为恢复策略产物，见 §5.5）。commitment 机制（衰减/门控）沿用现状，取值与语义不变。

步指针语义：current_step 指向第一个 status ∈ {pending, active} 的步；步被 fulfilled/skipped 后指针前进；全部步为 fulfilled/skipped → Plan 完成（kind=plan_completed 落 transitions；skipped 步在完成记录中逐个列明，**Plan 完成记录必须携带「含 N 个 skipped 步」标记**，防止 skip 被读成全额完成）。

### 5.4 连续失败计数的精确语义（修 §1 #11）

对当前步的一次 StepEvaluation 计为**一次失败**，当且仅当三条全满足：
(a) 本次行动与当前步**一致**（匹配 action_candidates）；
(b) 行动结果未使 success_condition 满足（fulfilled=False）；
(c) failure_condition 满足，或行动结果 ok=False（被拒/未命中），或（无 failure_condition 时）success_condition 明确求值为「不满足且已可判定」（leaf_report 中至少一叶为决定性 0，如 object_found 在一次已完成的搜查后为假）。

计数器 = 当前步的 attempts（落在 PlanStep 上，随步走，不再是计划级单计数器）。**清零/重置规则（穷举）**：
- 步被 fulfilled 或 skipped → 该步计数随步关闭而定格（审计保留），新步 attempts 从 0 起；
- 计划被 replace/abandon/完成 → 计数器随计划定格；
- **相关环境变化**：若本 tick 新感知事件与当前步条件的引用集（条件中出现的 object/belief/location/角色）相交，attempts 清零并强制在下一次行动前重估该步（reason="environment_changed" 落 transitions）——「环境变了，之前的失败不算数」从此有定义；
- 步骤无关的行动（不一致）：**既不计失败也不清零**（与现状一致，但这次是写进契约的选择而非实现偶然：无关行动不改变步的可达性，常识上不应赦免也不应加重）；
- 谓词求值为「尚不可判定」（如 belief 类步在无新信息时）→ 不计失败、不清零（记 evaluation 但 failed=False）。

blocked 进入条件：当前步 attempts ≥ retry_policy.max_attempts（缺省 2，与 BLOCK_THRESHOLD 同值，但从此是**每步可声明**的策略），或 failure_condition 声明 `"terminal": true` 且满足。进入时落 transitions kind=blocked（含 step_id、attempts、reason），计划状态置 blocked、blocked_info 填齐。

### 5.5 Blocked 恢复策略（PlanManager 管状态合法性，Provider/合成器提策略）

五种策略都是 PlanManager 上的显式状态转换，每种落 transitions（kind=recovery，带 strategy 与 reason），合法转换表如下（非法转换由 PlanManager 拒绝并记录，不许 provider 绕过）：

| 策略 | 转换 | 语义与审计要点 |
|---|---|---|
| retry | blocked → active（同一步） | attempts 清零后在原步重试；**重试总次数受该步 retry_policy.max_attempts 的第二层上限约束**：同一计划内对同一步的 retry 恢复最多 2 次，超过后 retry 不再是合法策略（防无限重试，审查 Plan 验收第 8 条） |
| replan | blocked →（旧计划 abandoned，reason="replanned"）+ 新计划 set | 新计划必须由 provider plan_update 或合成器在同一 tick 给出；goal_id 默认继承 |
| suspend | blocked → suspended | 必须同时给出 reactivate_when 条件（§3.3 谓词）；GoalEvaluator 在每 tick evaluate 时顺带检查 suspended 计划的再激活条件，满足 → suspended → active 并落行（reason="reactivate_condition_met"）。无再激活条件的 suspend 非法 |
| abandon | blocked → abandoned | 必须带 reason（沿用现有 reason 门控）；联动 GoalEvaluator 在下一次 evaluate 时按 §4.5 判定目标暂停/继续——abandon 计划 ≠ 放弃目标，两个记录分开 |
| skip | blocked → active（当前步标 skipped，指针前进） | 必须带 reason；被 skip 的步**不产生任何目标进度**（§4.3 的进度只认条件满足度，天然成立）；skip 后若指针走完，Plan 以「含 skipped」标记完成（§5.3） |

**默认自动策略（恢复不再只依赖 provider 开口）**：计划进入 blocked 时，PlanManager 立即按当前步 retry_policy.on_exhausted 排定默认策略，在**下一个 decide() 的计划评估点**自动执行（retry/suspend/replan-请求合成器/abandon 之一），并落 recovery 行（source="policy_default"）。provider（LLM 或 rule 合成器）可以在 blocked 后的第一个 decide() 中以 plan_update 的新字段 `recovery: {strategy, reason?, reactivate_when?}` 抢先提出不同策略，则以 provider 的为准（source="provider"）。rule 路径的默认策略来自步的 retry_policy 数据——**rule 模式从此能自洽地进出 blocked**（修 §1 #12）。现 provider `advance` 对 blocked 的「解阻+跳步」融合语义**废止**：advance 回归「提供者声称当前步已完成」的原义且只对 active 计划有效，对 blocked 计划发 advance 视为非法更新、记录并忽略（LLM 契约文本同步更新，见 §9 风险 3）。

### 5.6 审计新增

- plan_transitions 扩 kind：step_evaluated 之外，新增 recovery / blocked / step_skipped / plan_completed（含 skipped 计数）/ environment_reset。每次 StepEvaluation 落一行 kind=step_evaluated（after 快照含 StepEvaluation 全文：fulfilled/failed/reason/leaf_report/attempts）——§6 的 Plan Step Fulfillment Rate 等指标由此计算，不靠事后推断。
- goal_changes 扩 kind：activated / goal_failed / priority_change（其余沿用）。
- 决策 record 新增 candidate_scores（§3.6）。

### 5.7 Legacy 步与 LLM 计划的迁移规则

- 现存字符串步（rule 旧计划在 B1 后不再产生；LLM 自由文本步持续存在）在载入/产生时包装为 PlanStep{step_id: f"legacy:{i}", objective: 原文， action_candidates: [], success_condition: None, retry_policy: 缺省}。
- success_condition=None 的步：StepEvaluator 不做结果判定（fulfilled 恒 False、failed 恒 False），其步进**只**能由 provider 显式 advance 驱动（= 现行 LLM 行为，不回归），且在 step_evaluated 行中标记 legacy。这类步不进 blocked、不计失败——如实标注为「无条件步」，其占比是 §6 指标中的一个报告量（legacy step share），随场景数据化推进应下降。
- B1 的合成器步与 B2/B3 的全部新步都是条件步。酒馆的 _interpret 计划在 B1 随解释层改造一并消失，不做 legacy 保留。

## 9. 风险与难点

**风险 1：通用候选生成导致行为同质化（实验 3b 的教训）。**
3b 中三人同质的根因不是「太通用」，而是**根本没有目标驱动候选**：rule 候选按酒馆角色 id 生成，新角色一条都命中不了，全员只剩 observe/listen 基线，谨慎人格再把 observe 顶上去，于是人人观察。本设计的三重对策：① 候选从目标条件生成——只要目标类型不同（找物/求证/维持），候选集结构就不同；② InformationValue 按**本人**信念的不确定性计分——三人知道的东西不同，同一类行动的分数天然不同，这是分化的主引擎；③ 人格系数与披露门槛是角色数据。残余风险：同目标类型 + 相近人格的两个角色仍会趋同——那是理性趋同而非机制缺陷，用指标 13（Behavioral Diversity，含按目标类型分组的附表）监测，若 B4 中出现「同目标组内签名重合度 > 0.9」再议。**禁止的应对**：给某个角色加专属候选把行为「掰开」（违反 D3）。

**风险 2：酒馆涌现链（士兵读信 → 贪腐信念）在通用化后是否还出现。**
逐环核对新机制下的承接者：① 士兵获得 mayor 证言：merchant/soldier 的发言候选来自 learn_mayor_truth / gain_business 等目标的 belief 类模板 + claims 声明（mayor 命题的 assert 类）——有人会说；② 士兵 suspicion 上升并去后屋：suspicion 的来源改为通道二/三的通用增量（inquire 指向、deny 矛盾），search 候选来自 complete_investigation 中 object 类子条件（信的 object_found）+ InformationValue（对信的存在/位置不确定）——会去搜，但**时机不再由写死的 +0.55 suspicion 门控保证**，可能更早（没等证言就去）或更晚；③ 搜到信：客观事实，search 数据驱动，不依赖代码——必然成立（只要他去搜）；④ 读信后 mayor_embezzled 0.6：reveals 声明承接；⑤ 摊牌：belief 类模板在 confidence ≥ 0.8 阈值比时产 confront 候选 + selected goal 的 GoalAlignment——大概率出现。**诚实的风险点**：链的「顺序美」是旧规则手工调参（门控阈值、加分量级）的产物，通用机制下链可能乱序（如先搜后听）或在个别种子 20 tick 内走不完。对策口径钉死：B1/B3 的种子组逐环报告；若某环系统性缺失，先归因到通用项（InformationValue 权重、人格数据）并只许调**通用系数或角色数据**；缺环若来自机制缺失（如没有「向同场者打听物品」的模板），补的是通用模板，不是酒馆分支。若最终链在个别种子断裂，如实写入实验报告并与 V0.2-A 的 5/5 对照——**不许为了复现旧轨迹把任何酒馆语义塞回去**。

**风险 3：LLM 路径与新契约的兼容。**
受影响面：① PlanState.steps 由 list[str] 变为 list[PlanStep]——DecisionContext 的 JSON 形状变了，两家 LLM 的 SYSTEM_TEMPLATE/_JSON_CONTRACT 中描述 plan 的文本必须同步（现状两处文本分别维护，gemini 从 openai_provider import SYSTEM_TEMPLATE、B1 实施时应把契约文本收敛为单一常量来源并加一条「两后端契约文本一致」的测试，防漂移）；② PlanUpdate 新增 goal_id/recovery 字段——extra="forbid" 已在位，旧模型输出不带新字段可兼容（新字段全可选），新字段的校验走既有修复重试通道；③ advance 对 blocked 的语义变更（§5.5）是**行为契约变更**：LLM 若沿用旧习惯对 blocked 计划发 advance，将被记录并忽略，计划改由默认策略处理——不会卡死，但要在契约文本中明示 recovery 字段才是正道，并在 mock-LLM 测试中覆盖；④ selected_goal_id 语义不变（仍是归属校验），但其「应填当前服务目标」的提示文本要与 priority_current 口径对齐；⑤ 多后端（gemini + 四家兼容）的 sanitize 映射表不涉及新字段，无需改动；⑥ 检查点/续跑：Goal/PlanState 的 schema 演进遵循 Belief 证据迁移的先例（新字段全缺省、旧 state 可载入），但**跨版本 resume 不作承诺**：run_meta 新增 engine_version 字段，--resume 校验版本不一致时明确拒绝（优于静默错乱）。

**风险 4：场景 C 的冻结协议。**
冻结时点：B3 阶段验收通过时。冻结对象：§7.4 所列文件的决策语义 + §3.3 谓词词汇表 + §3.1/§3.4 schema——冻结清单以文件哈希形式写入 B4 报告。C 的设计者：不得是 B1–B3 的实现者（防不自觉迎合实现）；建议由 Hu 或外部审查者按 schema 文档独立撰写数据，实现方在 C 数据交付前完成「合理行为预期」的预注册。C 运行期发现的问题分三类处置：① 崩溃/Resolver 拒绝类 bug——可修，修复后 C 须重跑且报告披露；② 决策语义问题（行为不合理但程序正确）——**不许改代码**，记为通用性未达标的证据，留待 B 之后的版本；③ C 需要 schema/谓词表之外的表达能力——自动记为「C 未通过：契约表达力不足」，缺口清单进未解决问题，**不许现场扩词**（扩词等于 C 不是零改动）。此协议的目的是让 C 的通过/不通过都有信息量，而不是又一次「跑通了就算」。

**风险 5：确定性与既有不变量。**
效用评分与条件求值全是纯函数 + 有序枚举；唯一的随机源仍是 provider 的 seeded RNG（抖动）。风险点在新代码的集合/字典迭代序——沿用 sorted() 纪律并以跨 PYTHONHASHSEED 测试守住（该测试在永不动清单内）。GoalEvaluator/StepEvaluator 的求值不得引入墙钟或全局计数器依赖（plan_seq 的全局计数器是现有先例，新增组件避免再添）。

**风险 6：指标口径断裂。**
M1（计划一致性）在 B3 换定义（步名谓词 → 模板匹配）、goal_completion_rate 在 B2 换分母、progress 换语义——三个数都与历史值不可直接比。各阶段报告必须新旧口径并列并注明断裂点；实验报告禁止把 B 版数字与 A 版数字画在同一条趋势线上而不加标注。

## 10. 不做事项与边界（沿用 V0.2-A 不采纳项 + 本版新增）

- 不做 src/ 重组、不改 ACP_* 配置命名、不建 LLM 路径的程序效用层（LLM 仍直选；效用评分只存在于 rule 生成器内部——审查 §4.5 的公式要求落在此处，与 V0.2-A 审查「不为 LLM 新造效用模块」的结论并不冲突：该结论针对的是给 LLM 输出再套一层程序选择，本版不做那件事）。
- 不实现 give/take 的物品转移语义（objects.movable 只是数据位）；不新增 negotiate/cooperate/hide/investigate 动词——能力表只含现有 VERBS。场景若需要「交接」类行为，以现有动词组合表达并在报告中注明近似。
- 不引入 LLM 自由增删目标/改优先级（priority_rules 是配置数据，不是模型输出）。
- goal deadline 仍不设到期语义；情绪模型不扩维（honesty 经 SocialCost 首次生效是顺带收益，不另建情绪系统）。
- Narrative Observer / Storyline Extractor / Script Writer 仍不在本版范围（审查 §十：V0.2-B 验收通过后才建议进入）。
